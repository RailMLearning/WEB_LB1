# Отчёт по лабораторной работе №3

Дата проверки: 12.10.2026. Вариант: Java EE / Hibernate.

## Цель работы

Перенести REST API системы студентов общежития на Java, заменить JSON-хранилище реляционной базой, добавить пользователей, JWT и разграничение доступа. Сохранить модель студента и бизнес-правила второй лабораторной.

## Модель хранения

`students`: внутренний `id`, `version`, уникальный строковый `isu`, ФИО, группа, общежитие, комната, дата, признак иностранца и заметки. Внутренний id позволяет изменить ИСУ, сохранив идентичность строки; `@Version` обнаруживает конфликт параллельного UPDATE.

`users`: id, уникальные username и email, password_hash, роль ADMIN/USER. Роль хранится строкой. Клиент получает UserDto без хеша пароля.

`refresh_sessions`: jti, SHA-256-хеш refresh JWT, срок и FK на пользователя. Связь many-to-one: много сеансов принадлежат одному пользователю. При удалении пользователя SQL FK удаляет его сеансы.

Начальная схема создаётся SQL при инициализации нового PostgreSQL-тома. Hibernate использует `validate`: проверяет схему, не пересоздаёт таблицы при каждом запуске. Импорт старого `server/db.json` автоматически не выполняется; прежние данные остаются в этом файле.

## Работа со студентами

Сохранены GET списка, GET по ИСУ, POST, PATCH, DELETE и QUERY. Добавлен PUT для полной замены. ИСУ остаётся строкой из 5–7 цифр. Создание и полная замена требуют обязательные поля; PATCH изменяет только переданные. Отсутствие поля отличается от явного null, false и пустых заметок.

Фильтрация поддерживает поля студента и псевдонимы group/grid, dormitory/dnum. Текстовые ФИО и заметки сравниваются по подстроке без учёта регистра, остальные — точно. Условия соединяются через AND. Поиск q работает по ФИО, группе, ИСУ и заметкам.

Сортировка задаётся sort/order, имя поля проверяется по допустимому списку. Пагинация задаётся page/size: page от нуля, размер 1–100, default 20. Массив в ответе сохранён для совместимости; количество совпадений и страница возвращаются заголовками X-Total-Count, X-Page, X-Page-Size.

GET получает условия из URL, QUERY — из JSON-тела. В обоих случаях используются один валидатор и один запрос репозитория. Значения фильтров не склеиваются в SQL, `%` и `_` экранируются как буквальные символы.

## Пользователи и токены

Регистрация проверяет логин, почту и пароль; создаёт только USER. Передача role отклоняется. Первый ADMIN создаётся из окружения при запуске; повторная инициализация не перезаписывает существующий пароль и не повышает USER автоматически.

Пароли хешируются BCrypt с индивидуальной солью. Учитывается ограничение 72 байта UTF-8; проверяется минимум 8 символов. Plaintext-пароль не хранится в таблицах, DTO или логах.

После входа выдаются access и refresh JWT. Подпись, issuer, expiration и назначение токена проверяет JwtService. Данные пользователя и текущая роль дополнительно читаются из БД. Refresh не принимается как access.

Refresh однократный: в транзакции блокируется строка, удаляется старый сеанс и создаётся новый. Повтор старого токена даёт 401. Logout отзывает refresh. Уже выданный access действует до своего expiration — эта семантика сохранена явно.

USER читает список, QUERY и досье. ADMIN имеет все действия. AuthFilter применяет @RolesAllowed до выполнения обработчика. Проверка не зависит от наличия кнопок на странице.

## Клиентский интерфейс

Добавлены вход, регистрация, отображение роли и выход. Токены хранятся в sessionStorage вкладки; fetch отправляет Authorization. При 401 клиент обновляет пару и повторяет запрос. Одновременные обращения используют один refreshPromise; устаревшие ответы не подменяют новый сеанс после выхода/входа.

USER не видит кнопок создания, редактирования и удаления. ADMIN работает с прежними формами. Добавлены поиск, сортировка, выбор страницы и размера. Бизнес-проверки и окончательная фильтрация выполняются на сервере. Закрытые модальные окна скрыты через visibility, пользовательские значения выводятся через textContent.

## Валидация, ошибки и логи

Сохранены проверки ИСУ, ФИО, группы, номеров, даты, boolean и заметок. Неверные типы, неизвестные поля и повторяющиеся параметры отклоняются. Уникальность защищена проверкой сервиса и UNIQUE БД.

```json
{"detail":[{"field":"fio","message":"Введите имя буквами."}]}
```

Статусы: 200, 201, 204, 400, 401, 403, 404, 409, 422, 500. Node возвращает 502 при недоступности Java API. Пустой поиск — 200 и пустой массив, отсутствующая конкретная запись — 404. У 204 нет тела.

RequestLog записывает метод, путь, статус и длительность без заголовка Authorization и auth-тел. Непредвиденные исключения записывает ErrorMapper; клиенту не раскрывается stack trace. Переменные окружения описаны `.env.example`; локальный `.env` и build-артефакты исключены из Git/контекста сборки.

## Выполненные проверки

12.10.2026:

- Сборка WAR и Docker; запуск трёх сервисов.
- 7 тестов JUnit: поля, типы, PATCH, параметры, BCrypt, подпись/срок/назначение JWT.
- 68 HTTP-проверок через Node-прокси: auth, все методы студентов, роли, ошибки, сортировка и страницы, QUERY, уникальность, конкурирующие INSERT и refresh, logout, пустое тело 204.

- Postman-коллекция запущена через Newman: 25 запросов, 27 assertions, 0 failures.
- OpenAPI проверена валидатором спецификации.
- После force-recreate backend сохранились студент, пользователь и refresh-сеанс; временный студент удалён.

Проверки работают с отдельными тестовыми студентами и удаляют их. Созданные тестовые пользователи остаются в локальной БД; тестовые утилиты сообщают это в README.
