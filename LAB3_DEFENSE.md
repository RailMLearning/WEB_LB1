# Лабораторная №3: ответы к защите

Вариант: Java EE / Hibernate. Реализация использует Jakarta EE 10 на WildFly, JPA с провайдером Hibernate, PostgreSQL и Java 17. Ответы относятся к коду `java-backend`, а не к прежнему Python-backend.

Для повторения: лекция №4 — слои, DTO и границы; №5 — процессы, потоки и обработка запросов; №6 — Java-аннотации, CDI, жизненный цикл и роли. Номера ниже — страницы PDF в `Presentation`. Детали JPA и JWT дополнены документацией, перечисленной в конце.

## 1. Java в серверной разработке и JVM

Java-код компилируется в байткод `.class`, который выполняет JVM. JVM управляет памятью, сборкой мусора, загрузкой классов и оптимизацией выполнения. Типы проверяются при компиляции, но входные данные HTTP всё равно нужно проверять во время выполнения.

Maven собирает наш проект в WAR `ROOT.war`. WildFly загружает WAR, создаёт компоненты, запускает JAX-RS и подключает Hibernate. Java не означает Spring: в нашей работе используется Jakarta EE. В Docker сервер выполняет Java 17, исходники компилируются с `release=17`.

Покажи `pom.xml`, `ApiApplication.java`, `Dockerfile`. В лекции №6, слайды 3–10, показано разделение HTTP-сервера, framework и приложения.

**Уточнение:** WAR — архив веб-приложения с классами и ресурсами. Его принимает сервер приложений; это не файл базы данных.

## 2. Spring Boot и Java EE / Jakarta EE

Spring Boot помогает собрать приложение на базе Spring с автоконфигурацией; часто приложение запускается вместе со встроенным сервером. Jakarta EE — набор спецификаций, которые реализует сервер приложений. Java EE — прежнее название платформы; современные API используют пакеты `jakarta.*`.

У нас WildFly предоставляет JAX-RS, CDI, JPA, JTA и EJB. Hibernate — реализация ORM/JPA. В `pom.xml` Jakarta API имеет scope `provided`: API нужен для компиляции, реализацию даёт WildFly. Spring-зависимостей нет.

Сравнение есть в лекции №6, слайды 3–10 и 42. `@Path` указывает ресурс, `@GET` — метод, `@Inject` — зависимость. Это не Spring `@RestController`, `@GetMapping` или `@Autowired`.

## 3. Классы, интерфейсы, наследование и полиморфизм

Класс задаёт поля и методы объектов. Интерфейс задаёт контракт поведения. Наследование позволяет расширить существующий класс, полиморфизм — обращаться к реализации через общий контракт.

`Student` — класс сущности с полями студента. `StudentDto` — класс внешнего представления. `ApiException extends RuntimeException` наследует поведение исключения. `AuthFilter implements ContainerRequestFilter` реализует интерфейс JAX-RS: сервер вызывает его `filter`, не зная нашей конкретной реализации.

`ErrorMapper implements ExceptionMapper<Throwable>` — другой пример контракта. `UserDto`, `AuthTokens`, `FieldError` — records: компактные неизменяемые носители данных с автоматически созданными компонентами и методами. `StudentDto` изменяемый, потому что валидатор собирает его поля при PATCH.

**Уточнение:** мы не создаём искусственное дерево наследования для всех студентов. Для ТЗ достаточно сущности, DTO и небольших сервисов.

## 4. Аннотации Java

Аннотация — метаданные класса, метода или поля. Сам символ `@` не выполняет бизнес-операцию: сервер или библиотека читает метку и применяет соответствующее поведение. Для чтения во время выполнения нужна retention RUNTIME.

| Аннотация | Где и что делает |
| --- | --- |
| `@ApplicationPath("/api")` | Задаёт корень JAX-RS API |
| `@Path`, `@GET`, `@POST`, `@PUT`, `@PATCH`, `@DELETE` | Выбирают HTTP-обработчик |
| `@Inject` | Передаёт зависимость CDI |
| `@Entity`, `@Id`, `@Column`, `@ManyToOne` | Описывают отображение JPA |
| `@Transactional` | Задаёт границу транзакции сервиса |
| `@RolesAllowed` | Задаёт разрешённые роли; наш фильтр проверяет их |
| `@Provider` | Регистрирует JAX-RS фильтр или mapper |
| `@Version` | Помогает обнаружить параллельное изменение сущности |

Нестандартный QUERY объявлен собственной аннотацией `@HttpMethod("QUERY")` с RUNTIME. Это метка маршрута, не query-параметр. Лекция №6, слайды 14–16, различает Java-аннотацию и Python-декоратор.

## 5. Dependency Injection и Inversion of Control

IoC означает, что создание компонентов и вызов их жизненного цикла контролирует контейнер. DI — способ передать компоненту зависимости, вместо создания их внутри каждого метода.

`StudentResource` получает `StudentService` через `@Inject`. Сервис получает репозиторий и валидатор. Репозиторий получает управляемый `EntityManager` через `@PersistenceContext`. Наш код не создаёт новый EntityManager или подключение PostgreSQL на каждый вызов.

`@RequestScoped` создаёт ресурс для запроса, `@ApplicationScoped` задаёт общий сервис в приложении. `AppConfig` — `@ApplicationScoped` CDI-компонент с методами чтения конфигурации; `AdminInitializer` — EJB `@Singleton @Startup`, который запускает инициализацию при deployment.

Смотри лекцию №4, слайды 45–46, и №6, слайды 7–13, 35. Важное различие: общий сервис не должен хранить выбранного студента в поле. Наши значения операций локальны.

## 6. Архитектура и слои

HTTP-слой принимает запрос и выбирает ответ. Сервис выполняет бизнес-операцию. Репозиторий работает с данными. DTO задаёт внешнее представление, сущность — отображение таблицы.

```text
StudentResource
→ InputValidator / StudentService
→ StudentRepository
→ EntityManager / Hibernate
→ PostgreSQL
```

Уникальность ИСУ относится к бизнес-операции и также обеспечена UNIQUE в базе. Проверка формата ИСУ относится к валидатору. Выбор 409 вместо 422 относится к HTTP-контракту. Изменять файл HTML репозиторий не должен.

Пакеты: `api`, `dto`, `model`, `validation`, `service`, `repository`, `security`, `config`. Лекция №4, слайды 10–15, 23–32, 39–43 и 57. Маленькие классы нужны для разделения обязанностей; отдельные интерфейсы для каждого репозитория этой работе не требуются.

## 7. Исключения и единый формат ошибок

Исключение прерывает обычный путь исполнения. Проверяемые исключения Java нужно обработать или объявить, RuntimeException не требует такого объявления. `ApiException` несёт HTTP-код и описание ожидаемой ошибки.

`ErrorMapper` — централизованный `ExceptionMapper<Throwable>`. Он находит `ApiException` даже внутри исключения контейнера, преобразует конфликт UNIQUE и `OptimisticLockException` в 409, непредвиденную ошибку — в 500. Внутренний stack trace пишется в лог, клиент получает общее сообщение.

```json
{"detail":[{"field":"isu","message":"Студент с таким ИСУ уже существует."}]}
```

400 — некорректное JSON-тело; 401 — не пройдена аутентификация; 403 — роль не разрешает действие; 404 — ресурс не найден; 409 — конфликт; 422 — поля неверны. 204 возвращается без тела, а не с JSON `null`.

Смотри `ApiException`, `ErrorMapper`, `InputValidator`; лекцию №4, слайды 42–43, и №6, 39–42.

## 8. Реляционная база: таблицы и ключи

Таблица содержит строки одного типа, столбцы задают свойства. Первичный ключ идентифицирует строку, внешний ключ ссылается на строку другой таблицы. UNIQUE запрещает повторение значения, NOT NULL — отсутствие обязательного значения.

У нас `students`, `users`, `refresh_sessions`. `students.id` — внутренний BIGSERIAL primary key; `students.isu` — уникальная строка внешнего API. Это разные идентификаторы: ИСУ разрешено изменить без изменения внутреннего id. `users.username` и `users.email` уникальны. `refresh_sessions.user_id` — внешний ключ на пользователя.

Смотри `schema.sql` и классы `model`. Дата хранится как DATE, номера как BIGINT, роль как строка ADMIN/USER. PostgreSQL сохраняет данные на именованном Docker-томе.

## 9. Связи сущностей

Один-к-одному: одной строке соответствует не более одной строки связанной сущности, обычно с UNIQUE на FK. Один-ко-многим: у одной строки много связанных строк. Многие-ко-многим: нужна таблица связей с двумя FK.

В нашем коде у пользователя может быть много refresh-сеансов; каждый сеанс принадлежит одному пользователю. `RefreshSession.user` помечен `@ManyToOne`, а `@JoinColumn(name="user_id")` задаёт FK. Обратного списка сеансов в `UserAccount` нет: для этой операции он не нужен.

`FetchType.LAZY` означает отложенную загрузку связи. Когда `AuthService.refresh` обращается к `session.user`, транзакция ещё открыта. Мы возвращаем DTO, поэтому клиент не обходит ленивую сущность и не получает passwordHash.

Связи один-к-одному и многие-ко-многим в нашем проекте не реализованы: объясни принцип, но не показывай несуществующие сущности.

## 10. ORM и Hibernate

ORM отображает объекты и их поля на таблицы и столбцы, помогает выполнять запросы, отслеживать изменения и сохранять их. JPA — спецификация API и правил; Hibernate — провайдер, который их реализует.

`@Entity Student` отображается на `students`. `@PersistenceContext` предоставляет EntityManager. `persist` добавляет новую сущность; изменение управляемой сущности отслеживается Hibernate; `remove` удаляет. `flush` отправляет накопленные изменения в БД, но не означает commit.

`StudentRepository` использует JPQL для поиска по ИСУ и Criteria API для фильтров. Значения передаются параметрами/выражениями Criteria, а имя сортировки сначала проверяется по списку допустимых полей. Пользовательская строка не склеивается в SQL-команду.

В `persistence.xml` явно указан `org.hibernate.jpa.HibernatePersistenceProvider` и JTA datasource. Схема создаётся SQL-скриптом; Hibernate с `validate` проверяет её соответствие.

**Уточнение:** ORM не заменяет индексы, транзакции и ограничения базы и не отменяет понимание SQL.

## 11. Транзакции и ACID

Транзакция объединяет операции: либо изменения подтверждаются, либо откатываются. ACID: atomicity — целостное выполнение, consistency — соблюдение ограничений, isolation — согласование параллельной работы, durability — сохранность подтверждённых данных.

`StudentService` и `AuthService` помечены `@Transactional`: контейнер открывает JTA-транзакцию вокруг вызова. RuntimeException обычно приводит к rollback. Например, изменение ИСУ при конфликте не должно частично сохранить другие поля.

Refresh также транзакционный: строка сеанса блокируется `PESSIMISTIC_WRITE`, старый сеанс удаляется, новый сохраняется. Если сохранить новый не удалось, удаление старого откатится. Два одновременных обновления одной пары не должны выдать две новые пары.

UNIQUE остаётся защитой от гонки создания с одинаковым ИСУ: проверка «уже есть?» не может сама гарантировать отсутствие параллельного INSERT. `@Version` помогает обнаружить параллельный UPDATE вместо молчаливого затирания.

**Уточнение:** flush — SQL ещё внутри транзакции; commit — подтверждение всей транзакции. Откат должен охватывать всё бизнес-действие.

## 12. Аутентификация и авторизация

Аутентификация отвечает на вопрос, кто обращается. Авторизация отвечает, что этому пользователю разрешено.

Вход проверяет username и BCrypt-хеш пароля, затем выдаёт JWT. `AuthFilter` проверяет access JWT, получает существующего пользователя из БД и сравнивает его текущую роль с `@RolesAllowed`. Поэтому скрыть кнопки в JS недостаточно: прямой запрос USER к POST/PATCH/DELETE тоже получает 403.

Нет токена, подпись неверна или срок истёк — 401. Токен действующий, но роль USER пытается изменить студента — 403. При регистрации роль не выбирается; поле `role` отклоняется, создаётся USER.

Роли берутся из БД, а не только из строки payload. Пример аутентификации и авторизации: лекция №6, слайды 44–51.

## 13. JWT, подпись, access и refresh

JWT состоит из header, payload и signature, соединённых точками. Header содержит алгоритм, payload — claims. Base64url не шифрует данные: payload можно прочитать без ключа. Подпись позволяет проверить целостность и происхождение.

`JwtService` использует JJWT и HS256, проверяет подпись, issuer, срок и назначение `type`. Claims включают subject id пользователя, issuedAt, expiration и jti. Пароля в JWT нет. Access имеет короткий срок, refresh — более длинный, задаются окружением.

`/auth/refresh` принимает refresh, проверяет сохранённый SHA-256-хеш и срок, удаляет старую строку и выдаёт новую пару. Повтор старого refresh даёт 401. Refresh нельзя передать в Authorization вместо access. При logout refresh отзывается; уже выданный access действует до expiration.

Frontend после 401 один раз обновляет пару и повторяет запрос. Общий `refreshPromise` объединяет одновременные попытки обновления. Токены в sessionStorage принадлежат вкладке и не отправляются сами: JS добавляет Bearer.

Лекция №6, слайды 45–46. Секрет HS256 знает backend; его нельзя добавлять в JS или публиковать в Git.

## 14. Роли и защита ресурсов

USER получает список, досье и выполняет QUERY. ADMIN выполняет все операции, включая создание, PUT, PATCH и удаление.

`StudentResource` имеет разрешения USER/ADMIN на уровне класса и ADMIN на изменяющих методах. `AuthFilter` сначала читает метку метода, затем класса. Результат проверки записывается в SecurityContext. Отсутствие metки на публичных auth/health/docs позволяет доступ без входа.

Роль нельзя назначить запросом регистрации. ADMIN создаётся из `.env` при первом deployment, а повторный запуск не сбрасывает его пароль. Если заданный adminUsername занят USER, приложение не повышает его автоматически.

Покажи USER-запрос DELETE через Postman: отказ должен исходить от backend. Разделение прав в интерфейсе — только удобство пользователя.

## 15. BCrypt, хеш и соль

Хеширование одностороннее: пароль не расшифровывают, а проверяют алгоритмом сравнения с хешем. Соль делает хеши одинаковых паролей разными; BCrypt хранит необходимые параметры и соль внутри строки хеша.

`Passwords.hash` использует BCrypt с cost 12. `verify` сравнивает введённый пароль с сохранённой строкой. В таблице `users` есть `password_hash`, plaintext-поля password нет. UserDto не содержит хеш.

BCrypt имеет ограничение длины: валидатор допускает максимум 72 байта UTF-8, а не 72 русские буквы. Поэтому 37 букв «я» уже превышают предел. Пароль не trim: пробел может быть частью пароля. Минимум — 8 символов.

Тест проверяет разные хеши для одинакового пароля, успешное сравнение и отказ для неверного пароля. Лекция №6, слайды 47 и 52.

## 16. Конфигурация и секреты

Параметры окружения отделяют сборку приложения от конкретных адресов и паролей. `.env.example` перечисляет нужные значения, `.env` хранит локальные секреты и исключён из Git и Docker build context.

DB_URL/DB_USER/DB_PASSWORD настраивают datasource. JWT_SECRET/ISSUER и сроки задают токены. ADMIN_USERNAME/EMAIL/PASSWORD задают первого администратора. API_PORT/FRONTEND_PORT задают публикацию портов. `AppConfig` читает окружение; datasource использует выражения `${env.NAME}` WildFly.

`tools/setup-env.ps1` генерирует случайные значения и не перезаписывает существующий файл. В Postman пароль admin вводится локально. Его нельзя записывать в отчёт или экспортированную коллекцию.

`RequestLog` пишет метод, путь, статус и длительность. Тела auth-запросов и Authorization в лог не пишутся. `ErrorMapper` пишет непредвиденные ошибки для диагностики. Общая тема конфигурации — лекция №4, слайд 51.

## Что показать преподавателю

1. Запуск трёх сервисов Compose, страницу и Swagger.
2. Регистрацию USER и вход ADMIN.
3. USER видит список и досье; прямой запрос изменения получает 403.
4. ADMIN создаёт, частично меняет и полностью заменяет студента.
5. Дубликат ИСУ даёт 409, неверное ФИО — 422, изменения не сохраняются.
6. Поиск, фильтры, сортировку, разные страницы и QUERY в Network/Postman.

8. Перезапуск backend: данные остаются в PostgreSQL.
9. Удаление даёт 204 с пустым телом.
10. Пакеты, связь refresh → user, транзакции и конфигурацию.
