# Лабораторная №4: ответы для защиты

Вариант Vue. Примеры относятся к `frontend/src`. Начать просмотр проекта удобно с `main.js`, потом
перейти к `router.js`, `stores`, `services` и страницам в `views`.

## 1. React, Vue, Angular и Svelte

Все четыре инструмента позволяют строить интерфейс из компонентов. React — библиотека, вокруг
которой выбирают дополнительные инструменты. Vue предоставляет реактивность и шаблоны, а Router и
Pinia решают маршрутизацию и общее состояние. Angular предлагает более цельную платформу с DI,
формами и маршрутизатором. Svelte переносит значительную часть работы в компиляцию компонентов.

У нас Vue 3: файл `.vue` объединяет логику, шаблон и при необходимости стили. `main.js` создаёт
приложение и подключает Pinia с Vue Router. Java backend при этом остаётся отдельным приложением, к
которому frontend обращается по HTTP.

## 2. SPA и клиентская маршрутизация

SPA загружает основной документ, а затем меняет отображаемые страницы средствами JavaScript. Vue
Router сопоставляет путь компоненту. При переходе на `/profile` браузер не получает новый
HTML-документ: меняется компонент внутри `RouterView`.

Используется `createWebHistory`, поэтому адреса обычные, без `#`. При прямом открытии
`/students/001234` Nginx возвращает `index.html`, после чего нужную страницу выбирает Router. Без
`try_files ... /index.html` обновление вложенного адреса приводило бы к ошибке веб-сервера.

## 3. Компоненты, props и события

Компонент отвечает за ограниченную часть интерфейса. `StudentTable` показывает строки,
`StudentFilters` — поля поиска, `ConfirmDialog` — подтверждение удаления.

Родитель передаёт данные вниз через props. Например, `StudentsView` передаёт массив студентов и
признак администратора в таблицу. Таблица не удаляет запись сама: она отправляет событие `delete`, а
страница выполняет операцию через API. Так отображение не смешивается с запросами. Изменять props
напрямую не следует: обновление запрашивается событием.

## 4. Жизненный цикл и Composition API

`<script setup>` — удобная форма Composition API. `ref` хранит реактивное значение, `computed`
вычисляет производное, `watch` реагирует на изменение, lifecycle hooks связывают действия с жизнью
компонента.

В `StudentsView` подписка создаётся в `onMounted`, а снимается в `onUnmounted`. В карточке студента
загрузка начинается после монтирования, а при уходе запрос отменяется. Если не выполнить очистку,
старый компонент может продолжить запросы или обработку событий.

## 5. Рендеринг, Virtual DOM и условное отображение

Vue преобразует шаблон в функции рендеринга. Они описывают дерево виртуальных узлов. После изменения
реактивных данных Vue обновляет нужные части настоящего DOM. При сравнении списков
`:key="student.isu"` помогает сопоставить запись с её строкой.

`v-if` добавляет или убирает часть дерева: например, сообщение об ошибке или диалог. `v-for` строит
строки массива. Интерполяция `{{ student.fio }}` показывает значение текстом. Мы не вызываем
`document.createElement` для каждой строки, как в старой реализации.

## 6. Реактивность Vue

Vue отслеживает чтение реактивных значений и обновляет зависящие от них вычисления и шаблоны. Для
объектов используется `reactive`, для отдельных значений и массивов — `ref`. В JavaScript значение
ref читается через `.value`; в шаблоне Vue разворачивает его автоматически.

Например, после изменения `items.value` таблица получает новый массив и перерисовывается. `computed`
вычисляет количество страниц по `total` и `size`. Vue-реактивность обновляет интерфейс, а RxJS
управляет последовательностью асинхронных поисковых запросов.

## 7. Локальное и глобальное состояние

Локальное состояние нужно одной части интерфейса: поля формы, открытие фильтров, текущая ошибка
сохранения. Оно хранится в компоненте.

Общие данные находятся в Pinia. `auth` хранит пользователя и сеанс, `students` — список, фильтры и
пагинацию. Поэтому переход в карточку и обратно не сбрасывает поиск. Страница регистрации не меняет
чужое состояние напрямую, а вызывает действие auth-хранилища. Pinia не заменяет backend:
окончательные данные и права проверяются сервером.

## 8. Реактивное и императивное программирование

В императивном варианте обработчик каждого ввода сам запускает запрос и вручную решает, какой ответ
показать. При быстром вводе старый ответ может прийти после нового.

В реактивном варианте события рассматриваются как поток. Мы описываем правила его обработки:
подождать завершения ввода, убрать повторы, переключиться на последний запрос, преобразовать
результат в состояние интерфейса. Эти правила находятся в `services/studentSearch.js`.

## 9. Observable, Observer, Subject, BehaviorSubject и Subscription

`Observable` представляет источник значений во времени. Observer получает `next`, `error` и
`complete`. `subscribe` подключает наблюдателя и возвращает `Subscription`. Её `unsubscribe`
прекращает получение данных и запускает очистку источника.

`Subject` одновременно принимает события и позволяет подписываться на них: у нас это явное
обновление списка. `BehaviorSubject` дополнительно хранит последнее значение и сразу отдаёт его
новому подписчику: так хранятся актуальные условия поиска.

## 10. Операторы RxJS в проекте

- `debounceTime(300)` ждёт паузу после последнего события ввода.
- `distinctUntilChanged` убирает повтор одинаковых условий поиска.
- `switchMap` переключает обработку на новый внутренний поток.
- `map` преобразует результат API в состояние списка.
- `startWith` сразу сообщает о начале загрузки.
- `catchError` превращает ошибку запроса в отображаемое состояние.
- `shareReplay` позволяет разделить последний результат между подписчиками.

Важно положение `catchError`: он находится внутри потока отдельной загрузки, поэтому ошибка API не
убивает весь поиск. После восстановления сервера можно нажать повтор запроса.

## 11. Hot/cold Observable и очистка

Cold-источник начинает работу для подписчика. Созданный нами Observable запроса создаёт
AbortController при подписке. Subject — hot-источник: события можно отправлять независимо от наличия
подписчиков.

`shareReplay({ bufferSize: 1, refCount: true })` разделяет поток и отключает источник, когда
подписчиков не остаётся. Страница обязательно вызывает `unsubscribe` при уходе. Функция очистки
Observable вызывает `abort`: это прекращает реальный fetch, а не только игнорирует его результат.
Обычный Promise сам по себе не предоставляет такой отмены.

## 12. Поиск и отмена устаревших запросов

При вводе меняется Pinia query, после чего новое состояние поступает в BehaviorSubject. Быстрые
изменения объединяются за 300 мс. Затем `switchMap` снимает подписку с предыдущего запроса. Его
cleanup вызывает AbortController, и подписчик больше не получает старый результат.

Отдельный Subject запускает повтор текущего поиска после удаления или по кнопке обновления. Запросы
и операторы не находятся в шаблоне Vue, поэтому поток можно проверить без браузера.

## 13. Валидация, ошибки и загрузка

Клиент проверяет ввод перед отправкой: формат ИСУ и группы, буквы в имени, положительные номера,
существующую дату, длину заметок и данные аккаунта. Проверка клиента улучшает UX, но не защищает API
от прямого запроса, поэтому сервер проверяет данные повторно.

У ошибки API есть статус, сообщение и список полей. 422 связывается с полями, 403 означает нехватку
прав, 404 — отсутствие записи. Сетевой сбой отличается от ошибки валидации. При запросе показывается
загрузка. Флаг `busy` и disabled защищают форму от повторной отправки; finally снимает блокировку и
после успеха, и после ошибки.

## 14. Аутентификация, авторизация и JWT

Аутентификация отвечает на вопрос, кто пользователь, авторизация — что ему разрешено. После входа
сервер выдаёт access и refresh JWT. Access отправляется в Authorization, refresh используется только
для получения новой пары и выхода.

В API-клиенте 401 вызывает refresh и один повтор. Одновременные 401 используют общий Promise. Версия
сеанса защищает от запоздавшего ответа после выхода. 403 не обновляет токен: действительный
пользователь может не иметь нужной роли. JWT подписан, но его payload не является зашифрованным
хранилищем секретов.

## 15. Защита маршрутов и роли

`router.beforeEach` сначала восстанавливает сеанс. `requiresAuth` отправляет гостя на вход,
`adminOnly` не допускает USER к форме создания или изменения. UI также скрывает недоступные кнопки.
Профиль показывает актуальную роль, полученную через API.

Одна маршрутизация не обеспечивает безопасность: пользователь может вызвать fetch вручную. Поэтому
Java AuthFilter проверяет access и роль на каждом защищённом запросе.

## 16. XSS, CSRF и хранение токенов

При XSS посторонний код исполняется в контексте сайта. Vue по умолчанию экранирует текст;
пользовательские заметки не вставляются через `v-html`. В браузерном тесте HTML в заметках должен
остаться текстом, а не создать элемент img.

CSRF использует автоматически отправляемые браузером учётные данные, например cookies. Наш API
получает Bearer из заголовка, который добавляет приложение. Это уменьшает классический риск
cookie-based CSRF, но не отменяет необходимости серверной защиты и HTTPS. sessionStorage доступен
JavaScript, поэтому XSS мог бы прочитать токены. Это ограничение решения, а не утверждение, что
sessionStorage абсолютно безопасен.

## 17. Организация frontend

Страницы связывают компоненты с действиями. Компоненты показывают данные и отправляют события. Pinia
хранит общее состояние, сервисы знают HTTP, валидацию и RxJS. Router отвечает за адреса. Так
API-клиент можно проверить отдельно от формы, а форму — переиспользовать для создания и
редактирования.

Пример: `StudentsView → StudentFilters → students store → studentSearch → students API`. Поток
возвращает состояние хранилищу, Vue обновляет StudentTable.

## 18. Dockerfile, образ и контейнер

Dockerfile описывает сборку. Образ — её результат с файлами и настройками. Контейнер — запущенный
экземпляр образа. Пересборка frontend не должна удалять PostgreSQL-данные: они находятся в отдельном
именованном томе.

В проекте отдельные контейнеры выполняют PostgreSQL, миграции, Java и Nginx. Это позволяет проверять
их готовность и смотреть журналы каждого сервиса отдельно.

## 19. Многоэтапная сборка и Nginx

В первой стадии Dockerfile используется Node: устанавливаются зависимости и запускается Vite. Во
вторую копируется только готовый `dist`, который раздаёт Nginx. Node и исходники Vue в
runtime-образе не нужны.

Nginx обслуживает JS/CSS, возвращает index.html для клиентских маршрутов и перенаправляет `/api` в
Java. И frontend, и API доступны браузеру с одного origin, поэтому разные внутренние контейнерные
порты не требуют запросов CORS из браузера.

## 20. Docker Compose, сеть и окружение

Compose создаёт общую сеть и сервисы. Имя `web` разрешается внутри этой сети, поэтому Nginx
обращается к `web:8080`. Для пользователя опубликован frontend-порт 8080; Java-порт на хосте по
умолчанию 8000. Внутренний и опубликованный порты — разные настройки.

Секреты приходят из `.env`, образец — `.env.example`. Публичные параметры frontend-прокси
подставляются в Nginx при запуске, JWT_SECRET остаётся только на сервере. Миграции ждут здоровую БД,
Java — успешные миграции, frontend — здоровую Java. `docker compose down` останавливает приложение,
а `down -v` дополнительно удаляет тома.

## Короткий порядок демонстрации

1. Открыть защищённый адрес без входа и показать перенаправление на `/login`.
2. Войти ADMIN, открыть список и карточку, добавить и изменить запись.
3. Показать поиск, фильтры по всем полям, сортировку и смену страницы.
4. Удалить только свою демонстрационную запись через подтверждение.
5. Открыть `/profile`, обновить страницу и показать сохранение сеанса.
6. Зарегистрировать USER и показать отсутствие изменяющих действий и страницу 403.
7. Открыть `studentSearch.js`, объяснить debounce, switchMap и cleanup.
8. Показать два этапа Dockerfile и правило Nginx для вложенных маршрутов.
