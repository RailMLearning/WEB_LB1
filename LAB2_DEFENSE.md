# Лабораторная №2: ответы к защите по текущему коду

Актуализировано 05.10.2026 по рабочим файлам после объединения изменений. Здесь объясняется фактическая реализация, включая её ограничения. Пути указаны относительно корня проекта.

## Сначала: что делает приложение

Приложение управляет студентами общежития. Node отдаёт HTML-страницу и статические файлы, а обращения `/api/` проксирует FastAPI. FastAPI обрабатывает запросы к API. Браузер собирает значения формы, отправляет JSON через `fetch`, получает ответ и обновляет таблицу. Сервер проверяет данные и сохраняет их списком в JSON-файле.

Путь создания записи:

```text
Нажатие «Сохранить»
→ formHandlers.js: обработчик submit
→ studentStore.js: saveStudent
→ POST /api/requests
→ api.py: create_request
→ validator.py: validate_student → formatter.py: format_student
→ student_manager.py: create_student → store.py: _update_students → _write_students
→ ответ 201 с JSON
→ updateTables → GET списка → строки таблицы
```

Если проверка не прошла, до записи файла выполнение не доходит. Сервер возвращает ошибку, форма остаётся открытой.

## 1. Python в серверной веб-разработке

**Короткий ответ.** Python выполняет серверную логику: получает запрос, проверяет данные, обращается к хранилищу и формирует ответ. HTML и JS отображаются и выполняются в браузере, Python работает в серверном процессе.

**В нашем проекте.** В `server/router/api.py` находятся функции для HTTP-запросов, в `server/validator.py` — проверки, в `server/student_manager.py` — операции со студентами, в `server/store.py` — работа с JSON. Например, `create_request` вызывает проверку и создание студента, затем возвращает Python-словарь, который FastAPI превращает в JSON-ответ.

Сервер запускается командой:

```sh
python -m uvicorn server.routers.serve:app --host 127.0.0.1 --port 8000
```

`server.routers.serve` — путь Python-модуля, `app` — объект приложения в нём. Uvicorn принимает HTTP-соединения и передаёт запросы ASGI-приложению FastAPI. FastAPI и Uvicorn — разные части: фреймворк приложения и сервер для его запуска.

## 2. FastAPI, Flask и Django REST Framework

**Короткий ответ.** Фреймворк предоставляет готовые средства маршрутизации, запросов и ответов, чтобы не писать HTTP-сервер вручную.

| Инструмент | Основная идея | В этой работе |
| --- | --- | --- |
| FastAPI | API с маршрутизацией, аннотациями типов и поддержкой async | Используется |
| Flask | Небольшой веб-фреймворк, к которому подбирают нужные компоненты | Не используется |
| Django REST Framework | Средства построения API поверх Django, в том числе сериализаторы | Не используется |

В `serve.py` создаётся `app = FastAPI()`, затем подключается `api_router`. Роутер объединяет связанные адреса. `server.cjs` отдаёт HTML по `/`, статические файлы по `/static` и проксирует `/api` на FastAPI. Страница открывается на 8080, backend работает на 8000. Jinja-рендеринг в текущей версии отключён; в HTML используются прямые пути к статике.

**Если спросят о Pydantic.** В прикладном коде нет собственных Pydantic-моделей студента. Мы разбираем JSON и проверяем словари функциями. Сам FastAPI имеет собственные зависимости; говорить «Pydantic вообще отсутствует в окружении» неправильно.

## 3. Типизация Python и аннотации типов

**Короткий ответ.** Python динамически типизирован: тип относится к объекту. Аннотация описывает ожидаемый тип, но сама по себе не превращает обычную Python-функцию в проверяющую типы функцию.

```python
def get_request(isu: str):
```

В `api.py` `isu: str` описывает строковый параметр пути. FastAPI использует аннотации при обработке запроса. ИСУ — идентификатор, а не величина для арифметики: строка `"001234"` сохраняет ведущие нули.

```python
async def create_request(request: Request):
```

`Request` сообщает FastAPI, что функции нужен объект запроса. Тело не описано моделью: `await request.json()` возвращает разобранные данные, а их содержимое проверяет `validate_student`.

В валидаторе используется `isinstance`. Отдельно запрещён `bool` для номера комнаты: в Python `bool` является подклассом `int`, поэтому одной проверки `isinstance(value, int)` недостаточно.

## 4. Модели данных: dataclass, Pydantic, словари и классы

**Короткий ответ.** Модель данных описывает состав сущности и правила её значений. Для этого необязательно создавать класс.

- Класс объединяет данные и поведение, экземпляр представляет отдельный объект.
- `dataclass` помогает создавать классы данных, автоматически добавляя некоторые методы; сам по себе не проверяет все значения по аннотациям во время выполнения.
- Pydantic-модель предоставляет проверку и преобразование данных по описанной схеме.
- Словарь хранит пары «ключ — значение», проверки для него можно написать отдельно.

**У нас используется словарь студента и список таких словарей.** Правила находятся в `validator.py`.

```json
{
  "isu": "001234",
  "fio": "Анна-Мария",
  "grid": "M3301",
  "dnum": 8,
  "rnum": 42,
  "expdate": "2026-09-28",
  "foreigner": false,
  "notes": ""
}
```

Это пример нормализованной записи, не содержимое реального файла. Форма обычно передаёт номера строками; сервер преобразует их в целые числа. `foreigner` принимает boolean или строки `"true"`/`"false"`, сохраняется boolean. `notes` необязательно при создании, по умолчанию пустая строка. Остальные поля обязательны.

**Важное различие.** JSON — формат сохранения и передачи, словарь — объект Python в памяти. Наличие класса само по себе не мешало бы хранению в JSON, но в нашей реализации классов студента нет.

## 5. Исключения и обработка ошибок

**Короткий ответ.** Исключение прерывает обычное выполнение и передаёт управление подходящему обработчику `except` или обработчику фреймворка.

В `_read_json_object` неверный JSON перехватывается и превращается в HTTP 400. Отсутствие студента вызывает:

```python
raise HTTPException(status_code=404, detail="Студент не найден")
```

`raise` выбрасывает исключение; это не обычный возврат словаря. В `serve.py` обработчики приводят ошибки к общему виду:

```json
{"detail": [{"field": "isu", "message": "Сообщение об ошибке"}]}
```

Для общей ошибки `field` равен `null`. Непредвиденное исключение даёт 500 с общим сообщением. Проверка студента обычно не выбрасывает исключение: она возвращает `(None, errors)`, а роутер превращает список ошибок в 422.

На клиенте `readStudentResponse` проверяет `response.ok` и выбрасывает JS `Error`. Обработчик формы ловит его в `catch`, показывает сообщение, а `finally` включает кнопки обратно. Важно: `fetch` не обязан выбрасывать исключение на 404 или 422; HTTP-статус нужно проверять самостоятельно.

## 6. Декораторы во веб-фреймворках

**Короткий ответ.** Декоратор — функция, которая применяется к другой функции или классу при объявлении. Во фреймворке он часто регистрирует обработчик.

```python
@api_router.post("/api/requests", status_code=201)
async def create_request(request: Request):
```

Декоратор связывает POST по этому пути с `create_request` и задаёт успешный статус 201. Он не означает «запустить создание студента прямо сейчас». Регистрация выполняется при загрузке модуля, обработчик вызывается при подходящем запросе.

`@app.exception_handler(HTTPException)` аналогично регистрирует обработку определённой категории исключений.

## 7. Контекст запроса и область видимости

**Короткий ответ.** У каждого вызова обработчика свои параметры и локальные переменные. Глобальные переменные модуля разделяются между обращениями в одном процессе.

В `create_request` переменные `body`, `student`, `errors` относятся к текущему вызову. `request` содержит сведения именно о поступившем запросе: тело, параметры URL, заголовки.

В `store.py` `DB_PATH` и `_students_lock` — переменные модуля. Блокировка общая для вызовов внутри процесса. Внутренняя функция `add_student` из `student_manager.py` использует `isu` и `value` из внешней `create_student`: это замыкание.

На фронтенде `originalIsu` хранит ИСУ открытой для редактирования записи, а `studentFilters` — выбранные фильтры. Это состояние интерфейса в текущей странице, а не серверная сессия.

## 8. Синхронный и асинхронный код

**Короткий ответ.** Синхронный вызов выполняется последовательно до завершения. Асинхронная функция может приостановиться на `await`, позволяя циклу событий выполнять другую работу, пока ожидается операция.

В `api.py` POST и PATCH объявлены через `async def`, потому что читают тело с `await request.json()`. В JS `await fetch(...)` ожидает ответ, а `await response.json()` — разбор тела.

`async` не делает любой код автоматически неблокирующим. `_load_students` и `_write_students` используют обычные файловые операции. Когда async-обработчик напрямую вызывает их, файловая операция может блокировать цикл событий. Обычные синхронные обработчики FastAPI выполняет иначе, через пул потоков, но это не распространяется автоматически на любую обычную функцию, вызванную внутри `async def`.

**Честное описание нашей работы:** асинхронное чтение запросов и запросы из браузера есть; асинхронного файлового хранилища нет. Для большого числа запросов файловый слой пришлось бы изменить.

## 9. Итераторы, генераторы и коллекции

**Короткий ответ.** Итерируемый объект позволяет обходить элементы. Итератор выдаёт следующий элемент через `next`. Генератор вычисляет элементы по мере запроса, не создавая заранее полный список результатов.

В `student_manager.py`:

```python
index = next((i for i, s in enumerate(students) if str(s.get("isu")) == key), None)
```

- `enumerate(students)` выдаёт индекс и студента.
- Выражение в круглых скобках выдаёт подходящие индексы по одному.
- `next(..., None)` берёт первый подходящий индекс, а при отсутствии возвращает `None`.
- Индекс 0 допустим, поэтому проверяется `index is None`, а не `if not index`.

`any(...)` в проверке уникальности прекращает обход при первом совпадении. Списковое включение в `student_manager.py:get_all_students` создаёт новый список. В `formatter.py` словарное включение создаёт новый словарь, не меняя входной объект. Множества `FIELDS` и `REQUIRED_FIELDS` позволяют находить неизвестные и отсутствующие поля через разность множеств.

**Короткий ответ.** Модуль — импортируемый файл Python; пакеты организуют модули в пространства имён. Разделение позволяет изменять одну обязанность, не переписывая всё приложение.

| `server.cjs` | Раздача HTML/статики и проксирование запросов к API |
| `server/router/api.py` | HTTP-методы, чтение запросов, выбор статусов |
| `server/validator.py` | Проверки студента и преобразование типов |

| `server/formatter.py` | Нормализация строк |

Поэтому не надо утверждать, что у нас полностью изолирована каждая бизнес-операция в отдельном слое.

## 11. REST и RESTful API

**Короткий ответ.** REST — архитектурный стиль взаимодействия с ресурсами. Адрес обозначает ресурс, метод — действие, статус — результат. В числе принципов — разделение клиента и сервера и независимость запросов от скрытого контекста сессии.

У нас коллекция студентов доступна как `/api/requests`, отдельная запись — `/api/requests/{isu}`. Название `requests` сохранено из ТЗ, хотя сущность — студент.

GET читает, POST создаёт, PATCH изменяет, DELETE удаляет. Данные передаются JSON. Один только JSON ещё не делает любой API RESTful. QUERY добавлен по ТЗ для поиска с условиями в теле запроса и не изменяет записи.

## 12. HTTP-методы и статусы

| Метод и путь | Результат |
| --- | --- |
| GET `/api/requests` | 200 и список, в том числе пустой `[]` |
| GET `/api/requests/{isu}` | 200 и студент либо 404 |
| POST `/api/requests` | 201 и созданный студент |
| PATCH `/api/requests/{isu}` | 200 и итоговая запись |
| DELETE `/api/requests/{isu}` | 204 без тела либо 404 |
| QUERY `/api/requests` | 200 и отфильтрованный список |

400 означает, что тело нельзя прочитать как JSON-объект. 422 — JSON разобран, но поля или фильтры неверны. 409 — конфликт с уже занятым ИСУ. 500 — непредвиденная серверная ошибка.

GET не меняет данные. Повторный DELETE возвращает 404 после успешного первого удаления, но итоговое состояние одинаково — студента нет. Это не противоречит идемпотентности удаления: речь о результате для состояния ресурса, а не об одинаковых статусах. Повторный POST с тем же ИСУ у нас даст 409. PATCH в общем случае не обязан быть идемпотентным; у нас он присваивает поля, но при смене ИСУ старый адрес перестаёт находить запись.

## 13. Маршрутизация, path- и query-параметры

**Короткий ответ.** Маршрутизация выбирает обработчик по методу и пути. Path-параметр является частью адреса ресурса, query-параметры идут после `?` и задают дополнительные условия.

```text
GET /api/requests/001234
GET /api/requests?group=M3301&dormitory=8
```

В первом случае `isu` равен `"001234"`. Во втором `request.query_params` содержит группу и общежитие. Значения параметров URL приходят строками. `group` и `dormitory` переводятся в имена полей `grid` и `dnum` в `filter_validator.py`.

Отдельный метод QUERY получает те же условия в теле:

```http
QUERY /api/requests
Content-Type: application/json

{"group":"M3301","dormitory":8,"foreigner":false,"rnum":42}
```

Это именно HTTP-метод QUERY, а не другое название query-параметров. Клиент выбирает его при более чем трёх непустых фильтрах. ТЗ требует переход при большом количестве параметров, но число три выбрано нами. Сервер не требует минимум четырёх полей для QUERY и принимает также пустой объект.

Маршрут зарегистрирован через `api_route(..., methods=["QUERY"], include_in_schema=False)`, поэтому его нет в Swagger. Проверять его можно через форму с четырьмя фильтрами или HTTP-клиентом.

## 14. JSON, сериализация и десериализация

**Короткий ответ.** Сериализация превращает структуру данных в формат для передачи или хранения. Десериализация восстанавливает структуру из этого формата.

| Где | Операция |
| --- | --- |
| JS перед отправкой | `JSON.stringify(student)` превращает объект в JSON-текст |
| Python при получении | `await request.json()` разбирает тело в Python-объекты |
| Python при чтении файла | `json.load(db)` читает JSON из файла |
| Python при сохранении | `json.dump(students, db, ...)` записывает JSON |
| JS при ответе | `await response.json()` разбирает ответ |

JSON использует `true`, `false`, `null`; Python — `True`, `False`, `None`. Объект JSON соответствует словарю, массив — списку. `Content-Type: application/json` сообщает формат тела, но сам не выполняет преобразование.

Ответ DELETE 204 не содержит JSON. Поэтому `readStudentResponse` возвращает `null` до вызова `response.json()`. Иначе корректное удаление выглядело бы ошибкой разбора пустого тела.

## 15. Серверная валидация и форматирование

**Короткий ответ.** Форматирование приводит допустимые данные к единому виду. Валидация решает, допустимы ли они вообще. Проверки в браузере нужны для удобства, на сервере — для всех клиентов, включая запросы в обход формы.

`format_student` убирает пробелы по краям строк, а в ФИО заменяет последовательности пробельных символов одним пробелом. Он не меняет регистр имени или группы.

`validate_student` проверяет:

| Поле | Правило |
| --- | --- |
| `isu` | Строка из 5–7 ASCII-цифр, ведущие нули сохраняются |
| `fio` | Непустое имя до 150 символов; слова начинаются с буквы; допускаются буквы, комбинируемые знаки, дефис и апостроф. Одного слова достаточно |
| `grid` | Заглавная латинская буква, 4 цифры, необязательная строчная латинская буква |
| `dnum`, `rnum` | Положительные целые числа до 9007199254740991; строки цифр преобразуются в int, bool и float отвергаются |
| `expdate` | Существующая дата YYYY-MM-DD, год от 1900 до 9999 |
| `foreigner` | Boolean или строки `"true"`/`"false"`, результат — boolean |
| `notes` | Строка до 500 символов, при создании может отсутствовать |

Верхняя граница номеров соответствует безопасному целому числу JavaScript, а не максимальному номеру комнаты по смыслу. Код проверяет формат группы, но не существование группы или комнаты в университете. Проверка даты не запрещает прошлые даты. Проверка ФИО проверяет символы, а не реальность имени.

Неизвестные поля отклоняются. При POST обязательные поля должны присутствовать. При PATCH `partial=True` разрешает пропуски, но явно переданный `null` не означает «не менять»: он проверяется и отклоняется для этих полей. После объединения изменений с текущей записью повторно проверяется весь студент. Пустая строка заметок допустима и очищает заметки.

Пример: `{"notes":""}` меняет только заметки. `{"fio":"Иван2"}` даёт 422 и ничего не сохраняет. Клиент показывает текст ошибки и при наличии `field` связывает её с соответствующим полем формы.

## 16. Stateless-архитектура

**Короткий ответ.** Серверу не нужно помнить предыдущие шаги конкретного клиента, чтобы понять следующий запрос. Каждый запрос содержит необходимые идентификаторы и данные.

PATCH содержит ИСУ в пути и изменения в JSON. DELETE содержит ИСУ в пути. GET/QUERY передают условия поиска. Сервер не запоминает, какого студента пользователь «выбрал раньше».

Это не означает отсутствие сохранённых данных. JSON со студентами — состояние ресурсов, оно нужно приложению. Запрет относится к необходимости скрытого контекста клиентской сессии для понимания запроса.

`originalIsu`, `saving`, `studentFilters` в браузере — временное состояние интерфейса. После перезагрузки таблица заново запрашивается с сервера. Уникальность ИСУ, окончательная проверка и фильтрация выполняются на сервере; клиентская проверка формы остаётся ради удобства. Само наличие или отсутствие cookies ещё не определяет stateless, но cookies как хранилище студентов у нас удалены.

## 17. Хранение и фильтрация в памяти и JSON

**Короткий ответ.** В памяти мы работаем с Python-списком, постоянная копия находится в JSON-файле. При чтении загружаем файл, при изменении сохраняем обновлённый список.

`_load_students` использует `DB_PATH`. Если файла нет, возвращает `[]`; повреждённый JSON не подменяется пустым списком, а приводит к ошибке. `_update_students` охватывает чтение, проверку и изменение блокировкой. Это предотвращает одновременные изменения списка потоками одного процесса.

`_write_students` создаёт временный файл рядом с целевым, записывает JSON, выполняет `flush` и `fsync`, затем заменяет целевой файл через `os.replace`. При ошибке до замены прежний файл не должен быть затёрт частично. Это не база данных, не история версий и не резервное копирование. `RLock` не защищает от другого процесса; используем один процесс Uvicorn.

Проверка фильтров в `validate_filters` и фильтрация в `students_filters`:

1. Преобразовать имена `group`/`dormitory` в поля записи.
2. Проверить значения фильтров и преобразовать номера/boolean.
3. Обойти список студентов.
4. Для каждого проверить все условия; при первом несовпадении перейти к следующему.
5. Вернуть список совпадений; если их нет — `[]` со статусом 200.

ФИО и заметки проверяются как подстроки через `casefold`, остальные поля сравниваются точно после преобразований. Условия соединяются логическим «И». При n студентах и k фильтрах выполняется до n × k сравнений; индекса и пагинации нет.

В Docker путь `/data/db.json` находится в именованном томе. Новый том начинается пустым; существующий локальный `server/db.json` туда автоматически не переносится. Обычное пересоздание контейнера не удаляет том; удаление самого тома удалит его данные.

## 18. CRUD и уникальный идентификатор

**Короткий ответ.** CRUD — Create, Read, Update, Delete: создать, прочитать, изменить, удалить. ИСУ связывает операции с конкретной записью независимо от её позиции в таблице и имени студента.

| Действие | JS | HTTP | Python |
| --- | --- | --- | --- |
| Создать | `saveStudent(student)` | POST | `create_request` → `create_student` |
| Прочитать список | `getAllStudents(filters)` | GET или QUERY | `_filtered_students` → `get_all_students` → `students_filters` |
| Прочитать одного | `getStudentById(isu)` | GET с ИСУ | `get_request` → `get_student_by_id` |
| Изменить | `saveStudent(student, originalIsu)` | PATCH | `patch_request` → `update_student` |
| Удалить | `deleteStudentById(isu)` | DELETE | `delete_request` → `delete_student_by_id` |

При создании `any(...)` проверяет занятый ИСУ. При изменении проверяется новый ИСУ, если он отличается от исходного. Запись остаётся на своём месте в списке, меняется её содержимое. Индекс списка используется только внутри операции; внешний идентификатор — ИСУ.

`originalIsu` нужен, чтобы при изменении самого ИСУ отправить PATCH на старый адрес, а новое значение передать в теле. Иначе сервер искал бы новую запись, которой ещё нет.

## Дополнительные вопросы по JavaScript

**Почему после await saveStudent вызывается updateTables?** Успешная запись уже сохранена сервером. Повторный GET получает актуальные данные с учётом текущих фильтров, вместо ручного изменения нескольких ячеек.

**Зачем preventDefault?** Чтобы отправка HTML-формы не перезагружала страницу стандартным способом. Обработчик сам отправляет fetch.

**Зачем saving?** Не даёт повторно отправить форму, пока предыдущая операция не завершена. Это удобство интерфейса; уникальность всё равно проверяет сервер.

**Зачем tableRequest?** У каждого обновления свой номер. Если медленный старый запрос завершится после нового, его результат не заменит актуальную таблицу. Запрос не отменяется, его устаревший ответ игнорируется.

**Зачем encodeURIComponent и URLSearchParams?** Первый кодирует ИСУ как часть пути, второй собирает безопасно закодированные параметры URL. Не нужно вручную склеивать пользовательские значения с `&` и `=`.

**Почему textContent?** Значения студента вставляются как текст, а не интерпретируются как HTML. Строка заметки с тегами не должна стать разметкой страницы.

**Почему после сохранения студент иногда исчезает?** Если изменённые поля больше не соответствуют выбранному фильтру, обновлённый сервером список его не включает. Это не означает удаление.

## Что сказать про Docker и запуск

Dockerfile описывает backend: Python, зависимости и запуск Uvicorn. Dockerfile.frontend описывает Node и раздачу страницы. Compose запускает оба сервиса, публикует порты 8000 и 8080 и подключает том к backend. Node обращается к `web:8000` внутри сети контейнеров. `EXPOSE` сам по себе не публикует порт; публикация задана в Compose. `0.0.0.0` внутри контейнера позволяет принимать соединения через проброшенный порт.

Команды запуска приведены в README. 05.10.2026 оба образа успешно собраны, оба сервиса запущены. Запросы прошли через Node-прокси; запись в именованном томе сохранилась после пересоздания backend. Проблемы запуска Docker Desktop с временными сокетами устранены пересозданием служебных каталогов с сохранением резервных копий. Это восстановление среды, а не часть логики лабораторной.

## Сценарий демонстрации

1. Открыть `http://127.0.0.1:8080/` и показать загрузку HTML и статики через Node.
2. Создать тестового студента с уникальным ИСУ, открыть его досье.
3. Попробовать создать второго с тем же ИСУ — получить 409, не потеряв форму.
4. Изменить комнату, перезагрузить страницу и показать сохранённое значение.
5. Выбрать один или два фильтра — показать GET в Network.
6. Заполнить четыре фильтра — показать QUERY и JSON-тело в Network.
7. Сбросить фильтры, удалить созданную тестовую запись, показать 204.
8. В HTTP-клиенте отправить неверное ФИО напрямую, минуя форму, и показать серверный 422.

Для демонстрации используйте отдельные тестовые записи. Понимание всей цепочки «форма → fetch → роутер → проверка → файл → ответ → таблица» важнее заучивания названий функций.
