## Сначала: что делает приложение

Приложение управляет студентами общежития. Node отдаёт HTML-страницу и статические файлы, а обращения `/api/` проксирует FastAPI. FastAPI обрабатывает запросы к API. Браузер собирает значения формы, отправляет JSON через `fetch`, получает ответ и обновляет таблицу. Сервер проверяет данные и сохраняет их списком в JSON-файле.

Путь создания записи:

```text
Нажатие «Сохранить»
→ formHandlers.js: обработчик submit
→ studentStore.js: saveStudent
→ POST /api/requests
→ FastAPI: StudentCreate → models.py: валидаторы → formatter.py: format_student
→ api.py: create_request → model_dump()
→ student_manager.py: create_student → store.py: _update_students → _write_students
→ ответ 201 с JSON
→ updateTables → GET списка → строки таблицы
```

Если проверка не прошла, до записи файла выполнение не доходит. Сервер возвращает ошибку, форма остаётся открытой.

## 1. Python в серверной веб-разработке

**Короткий ответ.** Python на сервере принимает данные запроса через веб-фреймворк, проверяет их, выполняет бизнес-операцию, обращается к хранилищу и возвращает HTTP-ответ. Браузер выполняет JavaScript и показывает интерфейс; Python работает в серверном процессе.

**Как запрос доходит до нашего кода.** Лекция №5, слайды 4–6 и 11, разделяет сервер и фреймворк. Uvicorn принимает соединение и разбирает HTTP. Через интерфейс ASGI он передаёт запрос FastAPI. Фреймворк выбирает маршрут, проверяет параметры и тело, вызывает обработчик, сериализует результат и отправляет ответ через сервер.

```text
Браузер → Node:8080 → Uvicorn:8000 → FastAPI
→ middleware → маршрут → проверка StudentCreate
→ create_request → create_student → JSON-хранилище
→ сериализация результата → HTTP 201 → браузер
```

Это путь корректного POST. Некорректные поля дают 422 до вызова `create_request`. Занятый ИСУ обнаруживается уже в бизнес-операции и даёт 409. Неверный JSON преобразуется нашим обработчиком ошибок в 400.

**В нашем проекте.** `server.cjs` отдаёт HTML и статику на 8080, а `/api/` проксирует на backend. `server/routers/serve.py` создаёт FastAPI-приложение и подключает роутер. `server/router/api.py` содержит HTTP-обработчики, `server/student_manager.py` — операции со студентами, `server/store.py` — чтение и запись JSON. Получение страницы и создание студента — разные HTTP-запросы.

```sh
python -m uvicorn server.routers.serve:app --host 127.0.0.1 --port 8000
```

`server.routers.serve` — импортируемый модуль, `app` — объект приложения в нём. ASGI задаёт интерфейс взаимодействия сервера и приложения: данные запроса находятся в `scope`, события поступают через `receive`, ответ передаётся через `send`. В нашем коде это взаимодействие обслуживают Uvicorn, Starlette и FastAPI; вручную функцию ASGI мы не пишем.

**Если спросят: «Почему нужен Uvicorn, если есть FastAPI?»** FastAPI задаёт правила обработки, Uvicorn обслуживает сетевые соединения и вызывает приложение. Их роли различаются. Аналогично backend — это не только набор адресов API: в него входят проверки, бизнес-правила и доступ к данным.

**Материал:** [Л1, слайды 11–12][л1]; [Л5, 4–8 и 11][л5].

## 2. FastAPI, Flask и Django REST Framework

**Короткий ответ.** Все три инструмента помогают строить серверные приложения, но дают разный набор готовых средств. Flask — компактная основа; Django REST Framework — REST-инструменты поверх Django; FastAPI — фреймворк API, использующий аннотации типов и Pydantic для проверки данных.

Сравнение из лекции №5, слайды 9–15:

| Инструмент | Как описать обработчик и данные | Обработка проверки полей | Использование в проекте |
| --- | --- | --- | --- |
| Flask | Функция с декоратором; тело читают через `request.get_json()` | Проверки вручную или отдельной библиотекой | Не используется |
| Django REST Framework | Например, `APIView` и `Serializer` поверх Django | `is_valid()` проверяет сериализатор; обычно ошибка 400 | Не используется |
| FastAPI | Функция с декоратором и параметром типа Pydantic-модели | Проверка до вызова функции; обычно ошибка 422 | Наш backend |

Лекция показывает Flask и DRF через WSGI, FastAPI через ASGI. Это сравнение рассматриваемых вариантов запуска, а не утверждение, что Django вообще не поддерживает ASGI. WSGI — синхронный интерфейс сервера и приложения; ASGI поддерживает асинхронное взаимодействие и, в частности, WebSocket. Конкретный способ обслуживания запросов зависит также от сервера и выбранного обработчика.

**В нашем проекте.** В `serve.py` создаётся `app = FastAPI()`, затем `app.include_router(api_router)` подключает маршруты. POST объявлен так:

```python
@api_router.post("/api/requests", status_code=201)
def create_request(student: StudentCreate):
```

FastAPI получает JSON, создаёт и проверяет `StudentCreate`, затем передаёт модель функции. `student.model_dump()` отдаёт словарь для бизнес-операции. Это соответствует примеру FastAPI на слайде 14 пятой лекции. Отличие нашего контракта: ИСУ хранится строкой, чтобы не потерять ведущие нули.

Swagger на `http://127.0.0.1:8000/docs` строится по схеме приложения. QUERY зарегистрирован с `include_in_schema=False`, поэтому его там нет. Jinja-рендеринг текущей страницы отключён: готовый HTML отдаёт Node на 8080.

**Если спросят: «Pydantic — это ещё один веб-сервер?»** Нет. Это библиотека моделей и проверки данных. FastAPI использует её, но соединения по HTTP принимает Uvicorn.

**Материал:** [Л5, слайды 9–15][л5]; [FastAPI: JSON-тело](https://fastapi.tiangolo.com/tutorial/body/), [Flask](https://flask.palletsprojects.com/en/stable/), [Django REST Framework](https://www.django-rest-framework.org/).

## 3. Типизация Python и аннотации типов

**Короткий ответ.** Python динамически типизирован: тип относится к объекту. Аннотация описывает ожидаемый тип, но сама по себе не превращает обычную Python-функцию в проверяющую типы функцию.

```python
def get_request(isu: str):
```

В `api.py` `isu: str` описывает строковый параметр пути. FastAPI использует аннотации при обработке запроса. ИСУ — идентификатор, а не величина для арифметики: строка `"001234"` сохраняет ведущие нули.

```python
def create_request(student: StudentCreate):
```

`StudentCreate` сообщает FastAPI схему JSON-тела: фреймворк создаёт проверенную модель до вызова обработчика. При ошибке обработчик создания вообще не выполняется. В QUERY остаётся `Request`: тело читается через `await request.json()`, затем проверяются фильтры.

В валидаторе используется `isinstance`. Отдельно запрещён `bool` для номера комнаты: в Python `bool` является подклассом `int`, поэтому одной проверки `isinstance(value, int)` недостаточно.

**Если спросят: «Аннотация типа запрещает передать другой тип?»** В обычной Python-функции нет: `def f(x: int)` само по себе не создаёт проверку. FastAPI и Pydantic читают аннотации и выполняют проверку отдельно. Динамическая типизация также не означает, что любые типы свободно смешиваются: например, строку и число нельзя сложить обычным `+` без подходящего преобразования.

Не путай `isu: str`, Python-декоратор `@api_router.get(...)` и Java-аннотацию `@GetMapping`: первый описывает ожидаемый тип, второй вызывает декоратор при объявлении, третья является метаданными для Java-инструментов.

**Не путай статическую проверку и проверку запроса.** Аннотации могут использовать IDE и анализаторы типов без выполнения программы. Pydantic проверяет реальные данные во время запроса. В лекции №3 TypeScript помогает описать контракт фронтенда, но даже типизированный клиент не освобождает Python-сервер от проверки чужого JSON. Наш фронтенд написан на обычном JS, TypeScript в нём нет.

**Материал:** [Л5, слайд 14][л5] показывает аннотацию Pydantic-модели; [Л3, 30–33][л3] — TypeScript, только для сравнения. Правила Python: [typing](https://docs.python.org/3/library/typing.html). Сравнение Java-аннотации и декоратора: [Л6, 14][л6].

## 4. Модели данных: dataclass, Pydantic, словари и классы

**Короткий ответ.** Модель данных описывает состав сущности и правила её значений. Для этого необязательно создавать класс.

- Класс объединяет данные и поведение, экземпляр представляет отдельный объект.
- `dataclass` помогает создавать классы данных, автоматически добавляя некоторые методы; сам по себе не проверяет все значения по аннотациям во время выполнения.
- Pydantic-модель предоставляет проверку и преобразование данных по описанной схеме.
- Словарь хранит пары «ключ — значение», проверки для него можно написать отдельно.

**У нас Pydantic-модель проверяет входные данные, а словарь и список словарей используются для хранения.** Поля и правила находятся в `models.py`; `validator.py` повторно проверяет итоговую запись после PATCH и проверяет отдельные значения фильтров.

```json
{
  "isu": "001234",
  "fio": "Анна-Мария",
  "grid": "M3301",
  "dnum": 8,
  "rnum": 42,
  "expdate": "2026-09-28",
  "foreigner": false,
  "notes": ""
}
```

Это пример нормализованной записи, не содержимое реального файла. Форма обычно передаёт номера строками; сервер преобразует их в целые числа. `foreigner` принимает boolean или строки `"true"`/`"false"`, сохраняется boolean. `notes` необязательно при создании, по умолчанию пустая строка. Остальные поля обязательны.

**Важное различие.** JSON — формат сохранения и передачи, словарь — объект Python в памяти. Pydantic-модель — экземпляр класса; `model_dump()` преобразует её в словарь. `json.dump()` затем записывает этот словарь в JSON. Использование класса не мешает хранению в JSON.

**Если спросят: «Зачем две модели?»** При POST нужно получить все обязательные поля, чтобы создать полную запись. При PATCH допустимо передать только `{"rnum": 302}`. `StudentUpdate` разрешает отсутствие остальных полей; `model_dump(exclude_unset=True)` не включит их в изменения. `exclude_unset` означает «не передано», а не «пустое»: явно переданные `false` и пустая строка заметок должны сохраниться.

`StudentValidation` содержит общие валидаторы, `StudentCreate` — поля создания, `StudentUpdate` наследует проверки и меняет обязательность полей. Строгий режим не разрешает случайно превратить число в ИСУ-строку; нужные преобразования номеров и boolean сделаны явно в валидаторах.

**Связь с DTO из лекции №4.** DTO описывает данные, передаваемые через границу приложения. `StudentCreate` и `StudentUpdate` выполняют роль входных DTO: определяют, что клиент может прислать. Это не таблица БД и не способ сохранения. Отдельного Response DTO и отдельного класса доменной сущности в нашем проекте нет: бизнес-операции используют словари и возвращают их FastAPI. Словарь удобен, но не задаёт контракт автоматически; модель делает состав и проверки явными.

**Материал:** [Л4, слайды 39–42][л4] о DTO; [Л5, 13–14][л5] о Serializer и Pydantic; [Pydantic: модели](https://docs.pydantic.dev/latest/concepts/models/), [exclude_unset](https://docs.pydantic.dev/latest/concepts/serialization/), [dataclass](https://docs.python.org/3/library/dataclasses.html).

## 5. Исключения и обработка ошибок

**Короткий ответ.** Исключение прерывает обычное выполнение и передаёт управление подходящему обработчику `except` или обработчику фреймворка.

В QUERY `_read_json_object` перехватывает неверный JSON и возвращает HTTP 400. Для POST/PATCH FastAPI разбирает тело сам; обработчик `RequestValidationError` в `serve.py` возвращает 400 для неверного JSON и 422 для недопустимых полей. Отсутствие студента вызывает:

```python
raise HTTPException(status_code=404, detail="Студент не найден")
```

`raise` выбрасывает исключение; это не обычный возврат словаря. В `serve.py` обработчики приводят ошибки к общему виду:

```json
{"detail": [{"field": "isu", "message": "Сообщение об ошибке"}]}
```

Для общей ошибки `field` равен `null`. Непредвиденное исключение даёт 500 с общим сообщением. Валидатор поля выбрасывает `ValueError`; Pydantic собирает такие ошибки, а FastAPI передаёт их в обработчик `RequestValidationError`. При повторной проверке после PATCH функция `validate_student` ловит Pydantic `ValidationError` и возвращает `(None, errors)`. Роутер превращает эти ошибки в 422.

На клиенте `readStudentResponse` проверяет `response.ok` и выбрасывает JS `Error`. Обработчик формы ловит его в `catch`, показывает сообщение, а `finally` включает кнопки обратно. Важно: `fetch` не обязан выбрасывать исключение на 404 или 422; HTTP-статус нужно проверять самостоятельно.

**Если спросят: «Чем return отличается от raise?»** `return` завершает текущую функцию и отдаёт обычный результат. `raise` прерывает обычный путь выполнения и ищет обработчик исключения. Поэтому после ошибки валидации нельзя продолжить запись «как будто всё прошло».

Лекция №5 показывает преобразование ошибок в HTTP-ответ на Python, а лекция №6 — аналогичную задачу на Java. У нас механизм другой — обработчики `@app.exception_handler(...)`. В сообщении 500 клиенту не отправляются traceback, путь файла и внутренние детали сбоя.

**Три разных причины ошибки из лекции №4.** Формат поля неверен — ошибка ввода, у нас 422. ИСУ уже занят — бизнес-конфликт, у нас 409. Не удалось прочитать или записать файл — непредвиденный сбой хранилища, у нас 500. Одинаковая структура ответа позволяет форме показывать ошибки одним способом, но коды сохраняют различие причин. Не нужно превращать любой сбой в 200 с текстом «ошибка».

## 6. Декораторы во веб-фреймворках

**Короткий ответ.** Декоратор — функция, которая применяется к другой функции или классу при объявлении. Во фреймворке он часто регистрирует обработчик.

```python
@api_router.post("/api/requests", status_code=201)
def create_request(student: StudentCreate):
```

Декоратор связывает POST по этому пути с `create_request` и задаёт успешный статус 201. Он не означает «запустить создание студента прямо сейчас». Регистрация выполняется при загрузке модуля, обработчик вызывается при подходящем запросе.

`@app.exception_handler(HTTPException)` аналогично регистрирует обработку определённой категории исключений.

**Разбор записи:** `@api_router.get("/api/requests")` сначала вызывает метод `get` и получает декоратор. При объявлении функции этот декоратор получает саму функцию и регистрирует маршрут. Упрощённый смысл: `get_requests = api_router.get("/api/requests")(get_requests)`.

Декоратор не обязан создавать обёртку: он может зарегистрировать функцию и вернуть её. В `models.py` `@field_validator` отмечает метод как правило Pydantic, а `@classmethod` передаёт классу метод с первым параметром `cls`.

**Если спросят: «То же самое, что аннотация Java?»** Нет. На слайде 14 Python-декоратор — исполняемый механизм, Java-аннотация — метка, которую ещё должен прочитать и обработать фреймворк. Похожие символы `@` не означают одинаковую работу.

**Не путай синтаксис и паттерн.** В лекции №4, слайды 62 и 64, Decorator — паттерн расширения поведения объекта через обёртку. Python-декоратор — конкретный механизм языка. Декоратор маршрута может просто зарегистрировать функцию, без новой обёртки на каждый запрос. Похожие названия не означают, что в нашей работе реализованы все классы паттерна из лекции.

**Материал:** [Л5, примеры на слайдах 12–14][л5]; [Л6, сравнение на 14][л6]; [декораторы Python](https://docs.python.org/3/reference/compound_stmts.html#function-definitions).

## 7. Контекст запроса и область видимости

**Короткий ответ.** Контекст запроса — данные конкретного обращения: путь, заголовки, тело и параметры. Область видимости определяет, где доступно имя переменной. Эти понятия связаны, но не одинаковы: локальная переменная обработчика может хранить данные запроса, а глобальная переменная существует дольше него.

**Разница фреймворков из лекции №5, слайд 16.** Во Flask `request` выглядит глобальным, но является прокси к текущему контексту запроса. В DRF объект приходит аргументом метода. FastAPI передаёт параметры согласно сигнатуре; объект `Request` можно запросить явно. Поэтому нельзя делать вывод, что любой импортированный `request` общий для всех пользователей.

**В нашем проекте.** В `create_request` параметр `student` и переменная `created_student` принадлежат конкретному вызову. В `get_requests(request: Request)` объект `request` содержит параметры текущего GET. Другой запрос получит другой вызов обработчика и свои локальные значения.

| Значение | Где живёт | Кто его разделяет |
| --- | --- | --- |
| `student` в `create_request` | Вызов обработчика | Текущий вызов |
| `request` в GET/QUERY | Текущий запрос | Код, обслуживающий этот запрос |
| `DB_PATH`, `_students_lock` | Python-модуль `store.py` | Вызовы в одном процессе |
| `originalIsu`, `studentFilters` | Открытая страница браузера | Код этой страницы |
| Студенты в JSON | Хранилище ресурсов | Клиенты приложения через API |

**Жизнь приложения и жизнь запроса.** На слайдах 17–18 общей настройке и пулу соединений отведена жизнь приложения, а соединению конкретного запроса — время запроса. Там показаны `lifespan`, `app.state` и `Depends` с `yield`. В нашей работе таких механизмов нет: общие настройки и блокировка находятся в модуле, файл открывается через `with` на время операции. Не надо приписывать проекту пул БД или зависимости, которых в нём нет.

**Замыкание в нашем коде.** В `create_student` вложенная `add_student` использует `isu` и `value` из внешней функции. Она передаётся в `_update_students` и выполняется под блокировкой. Так функция получает нужные значения через своё лексическое окружение. Лекция №2, слайды 33 и 36–38, показывает области видимости и замыкание в JS; Python-пример нужно объяснять по нашему коду.

**Если спросят: «Можно ли сохранить текущего студента глобально?»** Если это выбор конкретного пользователя, параллельный запрос может его перезаписать. Передавай ИСУ в каждом запросе и храни локальные данные в обработчике. Глобальная блокировка хранилища допустима, потому что она намеренно общая. При нескольких воркерах даже такие глобальные объекты будут отдельными в каждом процессе.

**Материал:** [Л5, слайды 16–18 и 22–25][л5]; [Л2, 33 и 36–38][л2]; [Л6, 35][л6]; [области видимости Python](https://docs.python.org/3/tutorial/classes.html#python-scopes-and-namespaces).

## 8. Синхронный и асинхронный код

**Короткий ответ.** Синхронная операция занимает выполняющий её поток до завершения. Асинхронный код может отдать управление на `await`, чтобы цикл событий обслуживал другие задачи во время ожидания. Само слово `async` не превращает обычное чтение файла в асинхронную операцию.

### Как это работает в нашей лабораторной

| Участок | Как выполняется | Почему |
| --- | --- | --- |
| GET, POST, PATCH, DELETE в `api.py` | Обычные `def`-обработчики в пуле потоков FastAPI | Работа с файлом синхронная |
| QUERY в `api.py` | `async def`, чтение тела через `await request.json()` | Нужно асинхронно получить тело |
| `_load_students`, `_write_students` | Обычные файловые вызовы | Асинхронного драйвера хранения нет |
| `await fetch(...)` в JS | Ожидание Promise сетевого запроса | Можно продолжать обработку событий страницы |

**Ограничение текущего QUERY.** После чтения тела он напрямую вызывает синхронную фильтрацию и чтение файла. На этом участке блокируется поток event loop; ожидание `threading.RLock` тоже может его блокировать. Следовательно, весь наш backend нельзя называть полностью неблокирующим. Для развития приложения такой участок можно вынести через `await asyncio.to_thread(...)` или изменить слой хранения. Эти изменения здесь не реализованы.

### Процесс, поток и корутина

Процесс — отдельная копия приложения со своей памятью. Потоки работают в памяти одного процесса и переключаются ОС. Корутины выполняются циклом событий и могут уступить управление при ожидании через `await`. Конкурентность означает, что несколько задач продвигаются за пересекающийся промежуток времени; параллельность — фактическое одновременное выполнение.

На слайдах 20–21 пятой лекции это сопоставлено с вытесняющим и кооперативным переключением. Пока одна корутина ждёт сеть, цикл может выполнять другую. Но длительный расчёт, `time.sleep()` или чтение файла прямо в `async def` мешают этому потоку обслуживать другие задачи. Примеры на слайдах 46–48 сравнивают обычный `def`, блокирующий `async def` и корректное асинхронное ожидание.

**GIL не заменяет блокировку.** В обычной сборке CPython GIL ограничивает одновременное выполнение Python-кода потоками одного процесса, но не делает цепочку «прочитать → проверить ИСУ → добавить → сохранить» одной атомарной операцией. Возможны переключения и потеря изменений. Варианты CPython без GIL также не отменяют необходимость согласовывать общие данные. Наш `_students_lock` защищает всю операцию изменения, а не только последнюю запись файла.

**Разница JS и Python.** Вызов JS-функции `async` запускает её до первого приостанавливающего ожидания и возвращает Promise. В Python вызов `async def` создаёт объект корутины: чтобы выполнить её, нужно дождаться её через `await` или запланировать задачу. Это различие отдельно отмечено на слайде 44 пятой лекции. Обработчик QUERY запускает фреймворк; вручную `asyncio.run()` внутри него не нужен.

**Если спросят: «Почему не написать везде async def?»** Это не ускорит синхронные файлы, зато может перенести блокирующую работу в event loop. Для обычных синхронных операций `def` подходит: FastAPI запускает такой обработчик в пуле потоков. При этом простой вспомогательный `def`, вызванный напрямую из `async def`, автоматически в пул не переносится.

**Материал:** [Л5, слайды 20–21, 27–34 и 42–49][л5]; [Л3, 6–17][л3]. Подтверждение выполнения обработчиков: [FastAPI: concurrency и async](https://fastapi.tiangolo.com/async/).

## 9. Итераторы, генераторы и коллекции

**Короткий ответ.** Итерируемый объект позволяет обходить элементы. Итератор выдаёт следующий элемент через `next`. Генератор вычисляет элементы по мере запроса, не создавая заранее полный список результатов.

В `student_manager.py`:

```python
index = next((i for i, item in enumerate(students) if str(item.get("isu")) == key), None)
```

- `enumerate(students)` выдаёт индекс и студента.
- Выражение в круглых скобках выдаёт подходящие индексы по одному.
- `next(..., None)` берёт первый подходящий индекс, а при отсутствии возвращает `None`.
- Индекс 0 допустим, поэтому проверяется `index is None`, а не `if not index`.

`any(...)` в проверке уникальности прекращает обход при первом совпадении. Списковое включение в `student_manager.py:get_all_students` создаёт новый список. В `formatter.py` словарное включение создаёт новый словарь, не меняя входной объект. Множество `FIELDS` в `filter_validator.py` используется для проверки имени фильтра. Обязательность полей студента теперь задаётся моделями Pydantic, а запрет неизвестных полей — `extra="forbid"`.

**Если спросят: «Чем список отличается от генератора?»** Список уже хранит элементы и позволяет обращаться по индексу. Генератор выдаёт их постепенно, хранит состояние обхода и обычно исчерпывается после прохода. Поэтому `any(...)`, `all(...)` и `next(...)` удобно использовать с генераторными выражениями: они могут остановиться раньше, не строя полный промежуточный список.

У нас `all(...)` требует совпадения всех фильтров, `any(...)` ищет хотя бы один занятый ИСУ. Сам список студентов всё равно загружается целиком из JSON: генератор внутри проверки не делает хранилище потоковым.

**Пример с фронтенда.** `Object.entries(filters).filter(...)` в `getAllStudents` создаёт массив непустых фильтров. JS `filter` на слайде 39 второй лекции и Python-списковое включение позволяют получить новую коллекцию, но их синтаксис различается. Генераторное выражение `(i for i, item in enumerate(students) if ...)` не строит заранее все индексы: `next` получает только первый найденный. При исчерпании итератор обычно сообщает `StopIteration`; второй аргумент `next(..., None)` заменяет это исключение значением `None`.

**Материал:** [Л2, слайд 39][л2] показывает коллекции JS. Python-итераторы и генераторы отдельно в лекциях не разобраны: [итераторы](https://docs.python.org/3/tutorial/classes.html#iterators), [генераторы](https://docs.python.org/3/tutorial/classes.html#generators).

**Короткий ответ.** Модуль — импортируемый файл Python; пакеты организуют модули в пространства имён. Разделение позволяет изменять одну обязанность, не переписывая всё приложение.

| Файл | Обязанность |
| --- | --- |
| `server/routers/serve.py` | Создание приложения, обработка исключений, подключение роутеров и статики |
| `server.cjs` | Раздача HTML/статики и проксирование запросов к API |
| `server/router/api.py` | HTTP-методы, чтение запросов, выбор статусов |
| `server/models.py` | Pydantic-модели и правила полей |
| `server/validator.py` | Повторная проверка записи и формат ошибок |
| `server/filter_validator.py` | Проверки фильтров и имена параметров |
| `server/formatter.py` | Нормализация строк |
| `server/student_manager.py` | Операции со студентами, уникальность ИСУ и отбор по проверенным фильтрам |
| `server/store.py` | Чтение и сохранение JSON, общая блокировка |
| `server/settings.py` | Путь к корню проекта |

У нас нет отдельного класса сервиса или репозитория. Проверка уникальности и логика изменения находятся в `student_manager.py`: вложенная функция передаётся в `_update_students` из `store.py` и выполняется под блокировкой на актуальном списке. Поэтому не надо утверждать, что у нас полностью изолирована каждая бизнес-операция в отдельном слое.

**Если спросят: «Зачем столько файлов для маленькой лабы?»** У каждого слоя своя причина изменяться: HTTP-контракт, правила студента и способ хранения. Если заменить JSON на БД, в первую очередь изменится хранилище, а путь POST и форма могут остаться прежними. Разделение не требует превращать каждую функцию в класс.

В лекции №4, слайды 10–11 и 23, контроллер обращается к сервису, сервис — к репозиторию. В нашем Python-проекте аналогичные обязанности выполняют `api.py`, `student_manager.py` и `store.py`. Java DI-контейнер у нас не используется: модули связаны импортами.

**Почему это архитектура, а не просто папки.** Лекция №4 различает low coupling и high cohesion. Первая идея — ограничить зависимости; вторая — собрать в модуле связанные обязанности. Роутер выбирает HTTP-статус, бизнес-слой решает, занят ли ИСУ, хранилище знает путь файла и способ записи. У нас зависимости выражены импортами и передачей функции проверки; DI-контейнера нет. Слайд 57 отдельно предупреждает об overengineering: для лабы не требуется создавать интерфейс и класс для каждой маленькой функции. Модуль Python — не то же самое, что ES-модуль JS: наши JS-файлы подключены обычными тегами `script`, без `type="module"`.

## 11. REST и RESTful API

**Короткий ответ.** REST — архитектурный стиль взаимодействия с ресурсами. Адрес обозначает ресурс, метод — действие, статус — результат. В числе принципов — разделение клиента и сервера и независимость запросов от скрытого контекста сессии.

У нас коллекция студентов доступна как `/api/requests`, отдельная запись — `/api/requests/{isu}`. Название `requests` сохранено из ТЗ, хотя сущность — студент.

GET читает, POST создаёт, PATCH изменяет, DELETE удаляет. Данные передаются JSON. Один только JSON ещё не делает любой API RESTful. QUERY добавлен по ТЗ для поиска с условиями в теле запроса и не изменяет записи.

**Если спросят: «Что ещё входит в REST?»** Ограничения REST включают клиент-серверное разделение, stateless, кэшируемость, единый интерфейс и слоистую систему; передача исполняемого кода клиенту является необязательным ограничением. При полном разборе единого интерфейса обсуждаются представления ресурсов и гипермедиа. В нашей учебной реализации используются ресурсные адреса, HTTP-методы, JSON-представления и независимые запросы; отдельной системы гипермедиа нет.

`/api/requests/001234` определяет студента, а не команду с именем «удалить». Именно DELETE говорит, какое действие выполнить.

**Как проверить по примеру.** `DELETE /api/requests/001234` говорит об операции над ресурсом с известным адресом. Конструкция вроде `GET /deleteStudent?isu=001234` смешала бы чтение с изменением ресурса и нарушила бы смысл GET. Node-прокси образует дополнительный слой между клиентом и FastAPI, но сам по себе не делает API RESTful. Важно соблюдать контракт ресурсов и запросов.

**Материал:** [Л1, слайды 12 и 29–32][л1] — клиент/сервер, ресурсы и методы. Полный набор ограничений: [REST у Роя Филдинга](https://ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style.htm).

## 12. HTTP-методы и статусы

| Метод и путь | Результат |
| --- | --- |
| GET `/api/requests` | 200 и список, в том числе пустой `[]` |
| GET `/api/requests/{isu}` | 200 и студент либо 404 |
| POST `/api/requests` | 201 и созданный студент |
| PATCH `/api/requests/{isu}` | 200 и итоговая запись |
| DELETE `/api/requests/{isu}` | 204 без тела либо 404 |
| QUERY `/api/requests` | 200 и отфильтрованный список |

400 означает, что тело нельзя прочитать как JSON-объект. 422 — JSON разобран, но поля или фильтры неверны. 409 — конфликт с уже занятым ИСУ. 500 — непредвиденная серверная ошибка.

GET не меняет данные. Повторный DELETE возвращает 404 после успешного первого удаления, но итоговое состояние одинаково — студента нет. Это не противоречит идемпотентности удаления: речь о результате для состояния ресурса, а не об одинаковых статусах. Повторный POST с тем же ИСУ у нас даст 409. PATCH в общем случае не обязан быть идемпотентным; у нас он присваивает поля, но при смене ИСУ старый адрес перестаёт находить запись.

**Если спросят: «В чём разница безопасного и идемпотентного метода?»** Безопасный метод по смыслу не меняет ресурс. Идемпотентный метод при повторении имеет тот же итоговый эффект, что и при одном вызове. Поэтому DELETE может быть идемпотентным, хотя он изменяет данные. Пустой результат поиска — 200 и `[]`, а отсутствие конкретного студента — 404.

На слайде 3 лекции №6 Java-пример отдаёт 400 при ошибке `@Valid`. В нашей лабораторной по ТЗ ошибки полей возвращаются как 422; переносить код статуса из примера другого фреймворка без проверки нельзя. 204 не содержит тела, включая JSON `null`.

**Группы статусов со слайда 34 первой лекции.** 1xx — промежуточные сообщения, 2xx — успех, 3xx — перенаправления и связанные ответы, 4xx — проблема запроса клиента, 5xx — проблема серверной обработки. В нашей демонстрации важны конкретные 200/201/204 и 400/404/409/422/500. Node также возвращает 502, если не может получить ответ backend. QUERY у нас только читает: фильтры в теле не превращают его в создание или изменение.

**Материал:** [Л1, слайды 29–34][л1]; [Л5, 12–15][л5]; [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html), [PATCH: RFC 5789](https://www.rfc-editor.org/rfc/rfc5789.html).

## 13. Маршрутизация, path- и query-параметры

**Короткий ответ.** Маршрутизация выбирает обработчик по методу и пути. Path-параметр является частью адреса ресурса, query-параметры идут после `?` и задают дополнительные условия.

```text
GET /api/requests/001234
GET /api/requests?group=M3301&dormitory=8
```

В первом случае `isu` равен `"001234"`. Во втором `request.query_params` содержит группу и общежитие. Значения параметров URL приходят строками. `group` и `dormitory` переводятся в имена полей `grid` и `dnum` в `filter_validator.py`.

Отдельный метод QUERY получает те же условия в теле:

```http
QUERY /api/requests
Content-Type: application/json

{"group":"M3301","dormitory":8,"foreigner":false,"rnum":42}
```

Это именно HTTP-метод QUERY, а не другое название query-параметров. Клиент выбирает его при более чем трёх непустых фильтрах. ТЗ требует переход при большом количестве параметров, но число три выбрано нами. Сервер не требует минимум четырёх полей для QUERY и принимает также пустой объект.

Маршрут зарегистрирован через `api_route(..., methods=["QUERY"], include_in_schema=False)`, поэтому его нет в Swagger. Проверять его можно через форму с четырьмя фильтрами или HTTP-клиентом.

**Если спросят: «QUERY — это query-параметр?»** Нет. Query-параметры — часть URL после `?`; QUERY — имя HTTP-метода в нашей лабе. Для четырёх фильтров JS отправляет JSON-тело с методом QUERY, а сервер применяет ту же фильтрацию. Отсутствие QUERY в Swagger не означает отсутствие обработчика: `include_in_schema=False` выключает только документирование маршрута.

В лекции №5, слайды 11 и 16, отдельно показаны поиск обработчика и получение параметров запроса. В FastAPI маршрутизация также отделена от того, откуда берутся значения: путь, query или тело.

**Чего сервер не получит.** Фрагмент после `#`, например `#details`, обрабатывается браузером и не передаётся как параметр HTTP-запроса. Порт также важен: `/api/requests` на странице `http://127.0.0.1:8080/` означает запрос на 8080, после чего Node перенаправляет его к FastAPI. Браузер сам по себе не угадывает порт 8000.

**Материал:** [Л1, слайды 18–22 и 31][л1]; [Л3, 21][л3]; [Л5, 11 и 16][л5]; `api.py` и `studentStore.js` для нашего порога QUERY.

## 14. JSON, сериализация и десериализация

**Короткий ответ.** Сериализация превращает структуру данных в формат для передачи или хранения. Десериализация восстанавливает структуру из этого формата.

| Где | Операция |
| --- | --- |
| JS перед отправкой | `JSON.stringify(student)` превращает объект в JSON-текст |
| Python при получении | FastAPI разбирает JSON и создаёт Pydantic-модель; QUERY читает `await request.json()` |
| Python при чтении файла | `json.load(db)` читает JSON из файла |
| Python при сохранении | `json.dump(students, db, ...)` записывает JSON |
| JS при ответе | `await response.json()` разбирает ответ |

JSON использует `true`, `false`, `null`; Python — `True`, `False`, `None`. Объект JSON соответствует словарю, массив — списку. `Content-Type: application/json` сообщает формат тела, но сам не выполняет преобразование.

Ответ DELETE 204 не содержит JSON. Поэтому `readStudentResponse` возвращает `null` до вызова `response.json()`. Иначе корректное удаление выглядело бы ошибкой разбора пустого тела.

**Если спросят: «model_dump уже возвращает JSON?»** Нет. `model_dump()` здесь возвращает Python-словарь. JSON-текст появляется позже: при сериализации HTTP-ответа FastAPI или при `json.dump` в файл. `model_dump_json()` был бы другим методом, но в этой реализации не нужен.

Лекция показывает автоматическое преобразование объекта в JSON через компонент фреймворка. У нас также можно вернуть словарь из обработчика, однако это не означает, что словарь и JSON являются одним типом данных.

**Обмен через fetch из лекции №3.** `JSON.stringify` превращает объект в текст для тела запроса. `await response.json()` читает тело и разбирает JSON; это отдельное асинхронное действие после получения `Response`. Метод не проверяет HTTP-успех за нас: у ответа 422 тоже может быть корректное JSON-тело с ошибкой. Поэтому в `readStudentResponse` есть и разбор тела, и проверка `response.ok`.

**Материал:** [Л1, слайды 27–28][л1]; [Л5, 11–14][л5]; [Л3, 13, 17 и 20][л3]; [json в Python](https://docs.python.org/3/library/json.html), [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259.html).

## 15. Серверная валидация и форматирование

**Короткий ответ.** Форматирование приводит допустимые данные к единому виду. Валидация решает, допустимы ли они вообще. Проверки в браузере нужны для удобства, на сервере — для всех клиентов, включая запросы в обход формы.

`format_student` убирает пробелы по краям строк, а в ФИО заменяет последовательности пробельных символов одним пробелом. Он не меняет регистр имени или группы.

Валидаторы Pydantic в `models.py` проверяют:

| Поле | Правило |
| --- | --- |
| `isu` | Строка из 5–7 ASCII-цифр, ведущие нули сохраняются |
| `fio` | Непустое имя до 150 символов; слова начинаются с буквы; допускаются буквы, комбинируемые знаки, дефис и апостроф. Одного слова достаточно |
| `grid` | Заглавная латинская буква, 4 цифры, необязательная строчная латинская буква |
| `dnum`, `rnum` | Положительные целые числа до 9007199254740991; строки цифр преобразуются в int, bool и float отвергаются |
| `expdate` | Существующая дата YYYY-MM-DD, год от 1900 до 9999 |
| `foreigner` | Boolean или строки `"true"`/`"false"`, результат — boolean |
| `notes` | Строка до 500 символов, при создании может отсутствовать |

Верхняя граница номеров соответствует безопасному целому числу JavaScript, а не максимальному номеру комнаты по смыслу. Код проверяет формат группы, но не существование группы или комнаты в университете. Проверка даты не запрещает прошлые даты. Проверка ФИО проверяет символы, а не реальность имени.

Неизвестные поля отклоняются. При POST обязательные поля должны присутствовать. При PATCH `StudentUpdate` разрешает пропуски; `model_dump(exclude_unset=True)` возвращает только явно переданные поля, но явно переданный `null` не означает «не менять»: он проверяется и отклоняется для этих полей. После объединения изменений с текущей записью повторно проверяется весь студент. Пустая строка заметок допустима и очищает заметки.

Пример: `{"notes":""}` меняет только заметки. `{"fio":"Иван2"}` даёт 422 и ничего не сохраняет. Клиент показывает текст ошибки и при наличии `field` связывает её с соответствующим полем формы.

**Если спросят: «Почему недостаточно проверки в JS?»** Запрос можно отправить из HTTP-клиента или собственного скрипта, вообще не открывая форму. Поэтому сервер проверяет данные до записи. Например, `{"fio":"Иван2"}` остаётся недопустимым даже при отключённом JavaScript.

`@model_validator(mode="before")` нормализует строки, затем `@field_validator(..., mode="before")` проверяет конкретные значения и разрешённые преобразования. `extra="forbid"` запрещает лишние поля. `StudentUpdate` проверяет PATCH, после объединения с существующей записью `validate_student` проверяет полного студента заново. Уникальность ИСУ проверяется бизнес-операцией на актуальном хранилище, а не только Pydantic.

**Структурная и бизнес-валидация.** На слайде 42 четвёртой лекции это две разные группы. «Комната — положительное целое число» — структурное правило. «ИСУ уже занят» — бизнес-правило, зависящее от остальных записей. Pydantic проверяет первую группу, `create_student` и `update_student` — вторую. В нашем коде нет проверки вместимости комнаты, регистрации пользователя или прав администратора: это примеры предметных правил из лекции, а не реализованные возможности лабы.

**Материал:** [Л4, слайды 42–43][л4]; [Л5, 12–15][л5]; [валидаторы Pydantic](https://docs.pydantic.dev/latest/concepts/validators/); `models.py` для правил нашей записи.

## 16. Stateless-архитектура

**Короткий ответ.** Серверу не нужно помнить предыдущие шаги конкретного клиента, чтобы понять следующий запрос. Каждый запрос содержит необходимые идентификаторы и данные.

PATCH содержит ИСУ в пути и изменения в JSON. DELETE содержит ИСУ в пути. GET/QUERY передают условия поиска. Сервер не запоминает, какого студента пользователь «выбрал раньше».

Это не означает отсутствие сохранённых данных. JSON со студентами — состояние ресурсов, оно нужно приложению. Запрет относится к необходимости скрытого контекста клиентской сессии для понимания запроса.

`originalIsu`, `saving`, `studentFilters` в браузере — временное состояние интерфейса. После перезагрузки таблица заново запрашивается с сервера. Уникальность ИСУ, окончательная проверка и фильтрация выполняются на сервере; клиентская проверка формы остаётся ради удобства. Само наличие или отсутствие cookies ещё не определяет stateless, но cookies как хранилище студентов у нас удалены.

**Если спросят: «Раз есть db.json, сервер уже stateful?»** Сохранённые ресурсы не нарушают stateless. Нарушение возникло бы, если бы сервер ожидал, что сначала клиент вызовет «выбрать студента», запомнил выбор в сессии и лишь потом понял PATCH без идентификатора. У нас нужный ИСУ передаётся в каждом запросе.

Лекция №3, слайды 24–25, различает cookies и браузерные хранилища. Cookies могут автоматически отправляться серверу, localStorage и sessionStorage сами по себе этого не делают. В первой лабе cookies использовались для данных студентов; во второй источником данных стало серверное хранилище, к которому обращаются через fetch. Тема токенов из лекций №1 и №6 не означает, что у нас реализована авторизация.

**Связь с воркерами из лекции №5.** Каждый процесс имеет свою память. Если хранить важные данные только в глобальном словаре одного воркера, POST может попасть в него, а следующий GET — в другой и не найти запись. Наш JSON сохраняется между запросами, но файловая блокировка работает только внутри процесса. Поэтому API не использует клиентскую сессию, однако запуск нескольких воркеров без изменения хранения всё равно не поддерживается. Stateless не обещает автоматической безопасности любого общего файла.

**Материал:** [Л5, слайды 22–25][л5]; [Л3, 24–25][л3]; [Л1, 37][л1]; [stateless в REST](https://ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style.htm#sec_5_1_3).

## 17. Хранение и фильтрация в памяти и JSON

**Короткий ответ.** В памяти мы работаем с Python-списком, постоянная копия находится в JSON-файле. При чтении загружаем файл, при изменении сохраняем обновлённый список.

`_load_students` использует `DB_PATH`. Если файла нет, возвращает `[]`; повреждённый JSON не подменяется пустым списком, а приводит к ошибке. `_update_students` охватывает чтение, проверку и изменение блокировкой. Это предотвращает одновременные изменения списка потоками одного процесса.

`_write_students` создаёт временный файл рядом с целевым, записывает JSON, выполняет `flush` и `fsync`, затем заменяет целевой файл через `os.replace`. При ошибке до замены прежний файл не должен быть затёрт частично. Это не база данных, не история версий и не резервное копирование. `RLock` не защищает от другого процесса; используем один процесс Uvicorn.

Проверка фильтров в `validate_filters` и фильтрация в `students_filters`:

1. Преобразовать имена `group`/`dormitory` в поля записи.
2. Проверить значения фильтров и преобразовать номера/boolean.
3. Обойти список студентов.
4. Для каждого проверить все условия; при первом несовпадении перейти к следующему.
5. Вернуть список совпадений; если их нет — `[]` со статусом 200.

ФИО и заметки проверяются как подстроки через `casefold`, остальные поля сравниваются точно после преобразований. Условия соединяются логическим «И». При n студентах и k фильтрах выполняется до n × k сравнений; индекса и пагинации нет.

В Docker путь `/data/db.json` находится в именованном томе. Новый том начинается пустым; существующий локальный `server/db.json` туда автоматически не переносится. Обычное пересоздание контейнера не удаляет том; удаление самого тома удалит его данные.

**Если спросят: «Почему нельзя просто перезаписать файл?»** Прямое перезаписывание может оставить обрезанный JSON при сбое. Временный файл и замена уменьшают этот риск. Отдельная блокировка нужна для гонки двух изменений: оба запроса могут прочитать старый список и последняя запись затрёт результат первой.

Наш `RLock` работает в одном процессе. Он не превращает JSON-файл в многопроцессную БД и не синхронизирует несколько контейнеров. Для лабораторной используется один процесс Uvicorn. Поиск выполняется обходом списка; для большого объёма данных понадобились бы другое хранилище и индексы.

**Гонка со слайда 33 пятой лекции применительно к нам.** Запрос A и запрос B читают один список. A добавляет первого студента, B — второго. Если каждый запишет свою копию без общей блокировки, последняя запись потеряет изменение другого запроса. `_update_students` держит блокировку при чтении, проверке уникальности, изменении и сохранении. `RLock` со слайдов 34 и 36 допускает повторный захват тем же потоком; у нас повторный захват для этой цепочки не требуется, обычный `Lock` тоже мог бы защитить такую секцию. Преимущество здесь даёт охват всей операции блокировкой, а не буква R. Фильтрация выполняется после получения снимка списка и не меняет JSON.

**Материал:** [Л5, слайды 8, 22–25, 33–36 и 49][л5]; [Л4, 30–32][л4]; [RLock в Python](https://docs.python.org/3/library/threading.html#rlock-objects); `store.py` и `student_manager.py` для фактического хранения и фильтров.

## 18. CRUD и уникальный идентификатор

**Короткий ответ.** CRUD — Create, Read, Update, Delete: создать, прочитать, изменить, удалить. ИСУ связывает операции с конкретной записью независимо от её позиции в таблице и имени студента.

| Действие | JS | HTTP | Python |
| --- | --- | --- | --- |
| Создать | `saveStudent(student)` | POST | `create_request` → `create_student` |
| Прочитать список | `getAllStudents(filters)` | GET или QUERY | `_filtered_students` → `get_all_students` → `students_filters` |
| Прочитать одного | `getStudentById(isu)` | GET с ИСУ | `get_request` → `get_student_by_id` |
| Изменить | `saveStudent(student, originalIsu)` | PATCH | `patch_request` → `update_student` |
| Удалить | `deleteStudentById(isu)` | DELETE | `delete_request` → `delete_student_by_id` |

При создании `any(...)` проверяет занятый ИСУ. При изменении проверяется новый ИСУ, если он отличается от исходного. Запись остаётся на своём месте в списке, меняется её содержимое. Индекс списка используется только внутри операции; внешний идентификатор — ИСУ.

`originalIsu` нужен, чтобы при изменении самого ИСУ отправить PATCH на старый адрес, а новое значение передать в теле. Иначе сервер искал бы новую запись, которой ещё нет.

**Если спросят: «Почему нельзя удалять по номеру строки?»** Строки меняются после фильтрации, сортировки или удаления другой записи. ИСУ идентифицирует самого студента. Два студента могут иметь одинаковые имена, поэтому ФИО также не подходит для уникального ключа.

При PATCH с новым ИСУ сначала находится запись по старому адресу, затем проверяется, не занят ли новый идентификатор. При конфликте возвращается 409 и прежняя запись сохраняется. При успешном изменении старый адрес возвращает 404, новый — обновлённого студента.

**Создание и изменение — разные контракты.** POST требует полный набор обязательных полей и создаёт новую запись. PATCH может передать только часть полей и меняет существующую. Форма при редактировании сейчас отправляет весь объект студента; сервер при этом поддерживает и настоящий частичный запрос вроде `{"rnum":302}`. Это полезно показать HTTP-клиентом: возможность API шире одного сценария формы.

**Материал:** [Л1, слайды 29–31][л1]; [Л5, 12–14][л5]; `api.py` и `student_manager.py` для CRUD и уникальности ИСУ.

## Дополнительные вопросы по JavaScript

**Что такое AJAX в этой работе?** Подход, при котором JS получает данные и меняет часть страницы без полной перезагрузки. Мы используем fetch и JSON, а не XMLHttpRequest или XML. Это соответствует лекции №3, слайдам 18–21 и 34.

**Почему catch не срабатывает сам на 422?** Полученный HTTP-ответ — состоявшийся сетевой обмен. fetch обычно возвращает `Response` и при ошибочном HTTP-статусе. `readStudentResponse` разбирает JSON, проверяет `response.ok` и сам выбрасывает `Error`; тогда обработчик формы попадает в catch. Сетевой сбой и HTTP-ошибка различаются. См. [Л3, слайды 13, 17 и 20][л3] и [MDN: fetch](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch).

**Почему await не «замораживает» страницу?** Текущая async-функция приостанавливается, пока ждёт Promise; браузер может обрабатывать другие события. Но длительный синхронный цикл в JS всё равно мешает интерфейсу. После завершения ожидания продолжение выполняется через механизм микрозадач. Это объясняется в [Л3, слайды 6–17][л3].

**Почему не возникает CORS между страницей 8080 и API?** Для браузера запрос относительный: страница на `127.0.0.1:8080` вызывает `/api/...` на том же origin. Уже Node делает серверный запрос к FastAPI на 8000. Серверный прокси не подчиняется браузерной Same-Origin Policy. Если JS начнёт обращаться прямо к 8000, порт изменит origin, и потребуются соответствующие разрешения CORS; при JSON и нестандартных методах возможен OPTIONS preflight. В `serve.py` есть CORSMiddleware, но обычный путь через Node работает в одном origin. См. [Л3, слайды 26–29][л3] и [Л1, 38–39][л1].

**Чем DOM отличается от исходного HTML?** HTML — полученная разметка, DOM — построенное браузером дерево объектов. JS создаёт строки таблицы и меняет текст через DOM; новый HTML-документ для каждого изменения не загружается. `textContent` показывает пользовательские данные текстом. `innerHTML` интерпретировал бы их как разметку и опасен для непроверенного ввода. См. [Л2, слайды 42–46][л2].

**Почему после await saveStudent вызывается updateTables?** Успешная запись уже сохранена сервером. Повторный GET получает актуальные данные с учётом текущих фильтров, вместо ручного изменения нескольких ячеек.

**Зачем preventDefault?** Чтобы отправка HTML-формы не выполняла стандартный переход. Обработчик собирает данные и сам отправляет fetch. `required` и другие HTML-ограничения помогают пользователю, но не заменяют проверку сервера. Формы показаны в [Л2, слайды 8–10][л2].

**Зачем saving?** Не даёт повторно отправить форму, пока предыдущая операция не завершена. Это удобство интерфейса; уникальность всё равно проверяет сервер.

**Зачем tableRequest?** У каждого обновления свой номер. Если медленный старый запрос завершится после нового, его результат не заменит актуальную таблицу. Запрос не отменяется, его устаревший ответ игнорируется.

**Зачем encodeURIComponent и URLSearchParams?** Первый кодирует ИСУ как часть пути, второй собирает безопасно закодированные параметры URL. Не нужно вручную склеивать пользовательские значения с `&` и `=`.

**Почему после сохранения студент иногда исчезает?** Если изменённые поля больше не соответствуют выбранному фильтру, обновлённый сервером список его не включает. Это не означает удаление.

## Что сказать про Docker и запуск

Dockerfile описывает backend: Python, зависимости и запуск Uvicorn. Dockerfile.frontend описывает Node и раздачу страницы. Compose запускает оба сервиса, публикует порты 8000 и 8080 и подключает том к backend. Node обращается к `web:8000` внутри сети контейнеров. `EXPOSE` сам по себе не публикует порт; публикация задана в Compose. `0.0.0.0` внутри контейнера позволяет принимать соединения через проброшенный порт.

Команды запуска приведены в README. Сборка и запуск двух сервисов проверены. После подключения Pydantic проверены POST, PATCH, QUERY и Swagger через запущенный backend; существующие записи сохранены. Сохранение JSON в томе также проверено после пересоздания backend. В `venv` лежит локальное окружение Python, оно исключено из Git; зависимости проекта задаются в `requirements.txt`.
