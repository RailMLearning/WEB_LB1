# Ревью лабораторной №3

Дата: 12.10.2026. Область проверки: Java API, Hibernate/PostgreSQL, JWT и роли, общий frontend, Docker, OpenAPI и Postman. Основание: требования третьей лабораторной и фактический код проекта. Проверка исходников дополнена выполненными тестами; отдельный внешний аудит не проводился.

## Итог

Обязательные функции ТЗ реализованы и прошли описанные проверки. Блокирующие замечания, обнаруженные при запуске и ревью, исправлены. Результат относится к учебному локальному приложению и проверенным сценариям; это не утверждение, что код исчерпывающе проверен при любой нагрузке.

## Что проверено в коде

**Аутентификация.** JwtService проверяет подписанный JWT, issuer, тип access/refresh и expiration. Алгоритм ограничен HS256. Поддельная подпись и refresh в Authorization отклоняются. Пароли проверяются BCrypt, не сравниваются с plaintext и не возвращаются клиенту.

**Роли.** Все маршруты студентов защищены. Метки ADMIN на изменяющих методах имеют приоритет над USER/ADMIN на классе. Роль читается из актуального пользователя БД. Регистрация не принимает role; bootstrap не превращает уже существующего USER в ADMIN.

**Транзакции и гонки.** Сервисные операции находятся внутри @Transactional. UNIQUE остаётся последней защитой от двух одинаковых INSERT. @Version защищает UPDATE от молчаливого затирания при конфликте версий. Refresh использует PESSIMISTIC_WRITE; старая и новая строки меняются в одной транзакции. Параллельное использование одного refresh выдаёт одну новую пару, второй запрос получает 401.

**Данные и DTO.** Entity не отдаётся вместо UserDto; passwordHash и внутренние поля Student.id/version не входят в контракт студента. ИСУ строковый, поиск и сортировка не зависят от индекса таблицы. PATCH сохраняет пропущенные поля, false и пустые заметки; явный null проверяется и отклоняется.

**Запросы.** Параметры сортировки проверяются по списку. Условия Criteria и параметр JPQL не составляются из SQL-фрагментов пользователя. Размер страницы ограничен, порядок дополняется внутренним id для устойчивого результата. Дубликаты query-параметров и псевдонимов отклоняются. `%` и `_` в поиске экранируются.

**Клиент.** fetch проверяет HTTP-статусы через readStudentResponse, отдельно обрабатывает 204. Повтор после refresh выполняется один раз; 403 не вызывает цикл обновлений. Досье и таблица сохраняют защиту от устаревших ответов. Значения пользователя выводятся текстом. После выхода локальные токены удаляются, таблица очищается и формы закрываются.

**Конфигурация и журналы.** JWT_SECRET и пароли приходят из окружения, .env не включается в Git и Docker context. JWT_SECRET проверяется на минимальную длину. Логи запросов не содержат auth-body, пароль или Authorization. Ошибка 500 имеет общий текст, внутренний stack trace остаётся на сервере.

**Документация.** Стандартные операции есть в OpenAPI; схема валидна. QUERY описан x-query и отдельным запросом Postman. В коллекции нет настоящего adminPassword. README объясняет создание .env, первый вход, запуск, том PostgreSQL и проверку API.

## Ограничения и принятые решения

- Logout отзывает refresh, но не уже выданный access. Он действует до expiration; blacklist access-токенов здесь не реализован. Это отражено в README и ответах для защиты.
- Токены находятся в sessionStorage и доступны JS этой вкладки. Не реализованы HttpOnly refresh-cookie, восстановление доступа к аккаунту и MFA; ТЗ их не требует.
- Refresh-сессии хранятся в БД, поэтому механизм их ротации имеет серверное состояние. JWT не означает, что сервер вообще не хранит данных.
- Начальная SQL-схема рассчитана на новый PostgreSQL-том. Автоматических миграций для дальнейшей смены схемы нет; Hibernate validate проверяет соответствие. Старый JSON не импортируется автоматически и остаётся отдельным файлом второй лабы.
- OpenAPI 3.0 не имеет стандартного поля операции QUERY. Swagger отображает стандартные методы, QUERY демонстрируется Postman/браузером и описан расширением x-query.
- Текстовый поиск использует lower PostgreSQL/Java и зависит от Unicode/колляции БД; он не обещает полного равенства Python casefold для всех языков.
- Проверены функциональные и конкурентные сценарии, но длительный нагрузочный тест, отказ всей БД и внешний security-аудит не выполнялись. Общий mapper 500 проверен по коду; он не маскирует ошибку успешным статусом.
- Зарегистрированные тестовые USER остаются в локальной БД. Студенты тестов удаляются; существующие записи не используются как тестовые.
- Общий frontend перенесён на третью лабу. Старый Python API и его Dockerfile/Compose сохранены для справки, но не являются активным Java-backend.
